## OIDC でのログイン

いまは画面の前段に別の認証 (forward-auth) を置く前提で、denpa 自身は
ベーシック認証しか持っていません。

- **グループを引き継ぐ** — Entra ID 側のグループを見て、`admin` のグループに
  居る人だけ入れる。誰がログインしたかではなく、どのグループに居るかで決める
- **ストリームと WebDAV は今までどおり** — `/api/recordings/*/file` と `/dav` は
  OIDC にしません。VLC も Kodi も Infuse も、ログイン画面へのリダイレクトを
  扱えないためです。ここはこれまでどおりベーシック認証で守ります

## チューナーを開いたままにする (エージェントの .NET 化)

**mirakc は外れました。** 局と番組表を読むのも、チャンネルを選り分けるのも denpa の
仕事になり、チューナー側に残っているのは「掴む・裁く・流す」だけです
([architecture.md](architecture.md#チューナーエージェント))。

**エージェントの .NET 版は入りました** (`agent-dotnet/`)。bun 版と同じ口を持ち、
**同じ適合テストを通ります** (`agent/conformance.test.ts` — `AGENT_CMD` を
差し替えて2回走らせる)。Native AOT で実行ファイル1個、依存はありません。

ここまでで**選局の仕方は変えていません。** どちらも `recisdb` を選局ごとに
起こしていて、振る舞いは同じです。入れ替えるときは像を差し替えるだけで、
戻すのも同じ手間です。

.NET にして1つ増えたことがあります。**チューナーを自分で見つけられるように
なりました** — 定義が無ければ `/dev/dvb/*` を開いて `DTV_ENUM_DELSYS`
で受けられる方式を聞き、地上波か衛星かまで判別します。実機の PT3 で
adapter0/2 が ISDB-S、adapter1/3 が ISDB-T と正しく出ています。sysfs にも
`recisdb` にもこれを答える口は無く、**bun のままでは書けなかったところ**です。

**選局も復号も書けました** (`Tuning.cs` / `ChannelTable.cs` / `AribB25.cs`)。
デバイスを掴んだままチャンネルを変えられて、B25 も自分で解けます。どちらも実機で
確かめました (下の実測)。

残っているのは**繋ぎ替えだけ**です。選局の口 (`TunerPool`) はまだ `recisdb` を
起こしていて、そこを ioctl 側に差し替えると `recisdb` への依存が消えます。
**先に片方だけ繋いでも意味がありません** — 掴んだまま選局しても、解く側が
外部プロセスのままなら結局プロセスを起こすことになるからです。

### 掴んだままチャンネルを変える — **書けました。実機で確認済み**

実機のチューナーは PT3 で、カーネルの `earth_pt3` が**標準の Linux DVB (v5)** として
出しています (`/dev/dvb/adapterN/{frontend0,demux0,dvr0}`。chardev のデバイスは
1つもありません)。DVB API は**開いたまま `FE_SET_PROPERTY` で選局し直せる**ので、
チャンネルを変えるのに閉じる必要がありません。

ところが `recisdb` は**1回1チャンネルの使い捨て**です
(`recisdb tune --device … --channel … <出力>`。あとから指示を送る口はありません)。
mirakc も同じで、掴む相手が変わるたびにプロセスごと立て直しています。

開けっ放しにすると3つ手に入ります。

1. **掴み手が入れ替わる隙間が無くなる。** いまは「前のが終わってから次が開く」まで
   デバイスが宙に浮きます。そこへ別のものが割り込めますし、`recisdb` が生き残って
   掴んだままになる事故も実際にあります (スキャンで**プロセスグループごと**殺して
   いるのはこのためです。[architecture.md](architecture.md#チャンネルスキャン))
2. **1回の選局を何人でも読める。** 番組表・ロゴ・録画・視聴が同じ物理チャンネルなら
   1本で足ります。エージェントが持つ「誰が何を掴んでいるか」の帳簿と素直に噛み合います
3. ~~**衛星は同じ周波数の中の切り替えが只になるはず。**~~ **外れました。下の実測。**

**買えないものもはっきりさせておきます。同期そのものは短くなりません。**
周波数を変えれば PLL と復調の同期は必ず要ります。消えるのはプロセスの立ち上げと
デバイスを開く時間だけです。

#### 実測 (PT3 / `earth_pt3` / 実機)

掴んだまま、選局だけを繰り返したときの同期までの時間です
(`denpa-agent --tune /dev/dvb/adapter0/frontend0 BS15_0,BS15_1,BS01_0,BS15_0`)。

| 選局 | 同期 | 最初の1バイト | 同期バイト |
| --- | --- | --- | --- |
| BS15_0 (最初) | 229 ms | 108 ms | 100% |
| BS15_1 (**同じ周波数**) | 187 ms | 186 ms | 100% |
| BS01_0 (周波数を跨ぐ) | 198 ms | 139 ms | 100% |
| BS15_0 (戻る) | 188 ms | 104 ms | 100% |
| T27 / T21 (地上波) | 366–377 ms | 142 ms | 100% |

**「同じ中継の中なら只」は成り立ちませんでした。** TSID を変えるだけの
BS15_0→BS15_1 が 187 ms、周波数を跨ぐ BS01_0 が 198 ms で、**差がありません**。
`tc90522` は TSID を書き換えても選局の手順を丸ごとやり直す作りで、PLL を
掛け直さずに済むという読みが外れています。BS の総当たりが 1/4 になる、
という当ては消えました。

残る2つは残ります。**プロセスの立ち上げが消える**のと、**掴み手が入れ替わる
隙間が無くなる**ことです。後者は絵空事ではなくて、この実測をしている最中にも
`recisdb` が読み手の居なくなったあと生き残り、チューナーを 5 分間掴んだままに
なりました (手で殺しました)。掴んだままなら、そもそも誰も掴み直しません。

代わりに背負うもの:

- **B25 の解除を自分でやる。** いまはカードを使って `recisdb` が解いています。
  カードを持つのはエージェントだけ、というのは既定路線ですが、
  `libaribb25` 相当を抱えることになります
- ~~**選局表を自分で持つ。**~~ **持ちました** (`ChannelTable.cs`)。下記
- **口が2つになります** (下記)。ただしどちらも開いたままで済みます

既製の常駐 (tvheadend など) に乗せ替える手もありますが、あちらは番組表も録画も
持っているので、**mirakc を別の大きいものに替えるだけ**になります。欲しいのは
「開いたまま選局して、TSを配る」薄い層だけです。

#### 選局表 — **入りました**

チャンネル名から周波数を出す表です。これまで持っていたのは `recisdb` のほうで、
こちらは `--channel T27` と渡すだけでした。

**数字は `recisdb` から取りました。** 自分で導き直すより、**いま実機で選局できて
いるものと同じ数字**にすることのほうが大事です。

- 地上波 … `473142857 + (ch-13) × 6 MHz` **Hz で**
- BS … `1049480 + 38360 × n` **kHz で** (中継は 38.36 MHz 刻み)
- CS … `1613000 + 40000 × n` **kHz で** (40 MHz 刻み)

単位が2つあるのは DVB API の決まりです (地上波は Hz、衛星は kHz)。取り違えても
ioctl は通り、**ただ同期しない**ので気付きにくいところです。

衛星でもう1つ要るのが **TSID** です。1つの周波数に何本もの TS が相乗りしていて、
復調器は TSID を書いて選り分けます。ところが denpa が言ってくるのは `BS15_0` の
ような**相対番号**なので、ここで直します。引く先は2つあります。

1. **自分の `channels.json`** — スキャン結果には TSID が入っています。**こちらが勝ちます**
2. 焼き込んだ表 — まだ1度もスキャンしていないときだけ

`recisdb` は 2 だけを持っています。BS は再編があるので焼き込んだ表はいつか古くなり、
実際 `recisdb` の表には手元で受かっている `BS13_3` `BS21_3` `BS23_3` がありません。
**スキャンした人のほうが必ず新しい**ので、こちらを先に引きます。

### chardev も開いたままにできる。ただし DVB では代われない

**「開いたまま選局する」は chardev でも成り立ちます。** `px4_drv` の chardev は
1つの fd に対して選局と streaming の開始・停止を投げる作りで、
**閉じずに何度でも選局し直せます**。

```c
#define PTX_SET_CHANNEL     _IOW(0x8d, 0x01, struct ptx_freq)
#define PTX_START_STREAMING _IO(0x8d, 0x02)
#define PTX_STOP_STREAMING  _IO(0x8d, 0x03)

struct ptx_freq { int freq_no; int slot; };
```

`slot` が衛星のスロットなので、**`BS01_0`〜`BS01_3` の切り替えも
`PTX_SET_CHANNEL` 1回**です (DVB の `DTV_STREAM_ID` と同じ考え方)。
むしろ fd が1つで済むぶん DVB より単純で、frontend / demux / dvr を
別々に開く必要がありません。

**では DVB だけにすればいいかというと、それは駄目です。** 「Linux DVB で使える
PLEX のチューナーもある」のは本当ですが、**そうでないものが主力**です。

| 機材 | 口 |
| --- | --- |
| PT2 / PT3 (Earthsoft) | **DVB** (mainline の `earth_pt1` / `earth_pt3`)。実機はこれ |
| PX-S1UD (ISDB-T / USB) | **DVB** (mainline の Siano `smsusb` + `smsdvb`。firmware `isdbt_rio.inp` が要る) |
| PX-BCUD (ISDB-S / USB) | **DVB** (Linux 4.7 以降 mainline) |
| PX4 / PX5 / PX-MLT / e-better 系 | **chardev のみ** (`px4_drv`。作者自身が "not V4L-DVB" と書いています) |

USBの1本ものは DVB に載っていますが、**複数チューナーの PCIe・USB ボードは
`px4_drv` の chardev だけ**です。ここを落とすと「4本挿してある人」がまるごと
外れるので、**2つとも実装します**。

さいわい抽象は同じ形になります — *開く → 選局 → 流し始める → 読む → 選局し直す*。
違うのはその4つをどの ioctl で言うかだけなので、エージェントの中では
**backend を差し替えるだけ**で済みます (`ITuneDevice`)。

**2つとも書きましたが、確かめられたのは DVB だけです。** ここにある機材は PT3 で、
chardev のデバイスは1つもありません。`Px4Tuner` の値は `px4_drv` と `recisdb` の
`character_device.rs` から取ってあり、**実機に当てていません**。

### B25 の解除は `libaribb25`

**これも書けました** (`AribB25.cs`)。実機のカードで確かめてあり、地上波を
掴んだまま解いて **掛かっているパケットが 87.8% → 0.1%** になります (残る 0.1% は
最初の ECM で鍵が決まるまでの分)。

呼び方は関数ポインタの表です。`create_arib_std_b25()` が返す構造体の中身が
そのまま関数ポインタなので、C# からは `delegate* unmanaged` で直に呼べます
(`Marshal.GetDelegateForFunctionPointer` は使いません。遅いうえ AOT で気を遣う)。
**1日ぶんの写経で済む見込み**と書いていたところで、実際そのくらいでした。

**いま実機で動いているものそのものだからです。** `recisdb` は
[recisdb-rs](https://github.com/kazuki0824/recisdb-rs) → `b25-sys` →
[libaribb25](https://github.com/tsukumijima/libaribb25) という積み方で、
このカードとこの電波で解けているのは既にこの実装です。差し替えても
**復号の挙動が変わらない**のが何よりの利点で、他を選ぶ理由が見当たりません。

他の道と、採らない理由:

| 案 | なぜ採らないか |
| --- | --- |
| 元祖の `libarib25` (stz2012) | `libaribb25` はこれの手入れが続いている側。わざわざ古いほうを採る理由が無い |
| MULTI2 と ECM を自分で書く | カードとのやり取り (PC/SC) は書けても、MULTI2 を自前で持つ意味が無い |
| 外部プロセスのまま (いまの `recisdb`) | 呼べはするが、下の「1回だけ解く」と噛み合わない |

設計として押さえておくことが2つあります。

- **解くのは選局ごとに1回。** 同じチャンネルを3人が読むなら復号も1回で足ります
  (MULTI2 は CPU を食うので、読み手ごとに解くと台無し)。**エージェントの中に持つ**か、
  外部プロセスに逃がすなら**選局ごとに1つ**にします
- **番組表とロゴには要りません。** PSI/SI (EIT・SDT・NIT・CDT・DSM-CC) は
  スクランブルされていないので、番組表集めもロゴ集めもカード無しで回ります。
  **カードが死んでいても番組表は埋まる**、という切り分けはそのまま残せます

#### カードは1枚でいい。**鍵を配る口を入れました**

想定しているのは「1台に4本挿す」ではなく、**拠点ごとにエージェントとチューナーが
あって、それが何箇所かある**形です。そうなるとカードは1箇所にしかありません。

そこで**カードごと持っていく代わりに、ECM を投げて鍵を貰います**
(`CardShare.cs`)。

```text
拠点B (カード無し)                     拠点A (カードあり)
  選局 → TS ─┬─ MULTI2 で解く          B-CASカード
             └─ ECM 200B ──────────→  proc_ecm
                鍵 16B  ←──────────
```

- **線に乗るのは鍵のやり取りだけ。** ECM は 200 バイトほど、返るのは 16 バイト
- **重いほうは動かしません。** MULTI2 は TS 全部に掛かるので各拠点の手元に残す
- **同じ ECM には同じ鍵を返します** (数秒だけ覚える)。衛星は全国で同じ電波なので、
  3拠点が同じ BS を見ていてもカードに聞くのは1回で済みます。**拠点が増えるほど効きます**

差し込み口は libaribb25 が用意してくれていました。カードは `B_CAS_CARD` という
**関数ポインタの表**で渡す作りなので、`proc_ecm` だけ別のところへ投げる表を作って
渡せば、復号の本体は何も変えずに済みます。

実機で確かめました。**カードを持っていない側として起こしたほうが、持っている側から
鍵を貰いながら 88.2% → 0.1% まで解けます。**

```sh
denpa-agent --tune /dev/dvb/adapter1/frontend0 T27 --decode --card http://拠点A:25252
```

**配る側は denpa ではなくエージェントです。** リーダーは USB の機材で、機材に
触るのはエージェント、という境界のままにしたいのが1つ。もう1つは、denpa (bun) から
PC/SC を触るには結局ネイティブの口を足すことになり、**既にカードを読めるものが
あるのに二重に持つ**ことになるからです。カードだけ刺さっていてチューナーが1本も
無いマシンでも、エージェントを1つ置けばそれが配り役になります。

**拠点にカードがあるならそれを使います。** そのほうが速く、配り役が落ちても
録れます。`--card` を指定しなければ手元のカードを読むので、**既定は今までどおり**です。

なお B-CAS カードの貸与条件は受信機ごとなので、**世帯をまたいで配るのは
グレー**です。手元の拠点をまとめる範囲で使うものと考えています。

#### カードを denpa 側に持たせない理由

**「1枚のカードで何本ものチューナーを解く」は、いまも既にそうなっています。**
カードを掴むのは pcscd で、pcscd は口を1つずつ順番に貸します。チューナーが4本
あっても、カードに用があるのは ECM が変わるとき (数秒に1回・数十ms) だけなので、
1枚で足ります。**カードが1枚だからエージェントに置けない、ということはありません。**

そのうえで、解くのをエージェント側に置く理由は3つあります。

1. **カードはあちらにしかありません。** リーダーは USB で、機材のあるマシンに
   刺さっています。denpa 側に持たせると、リーダーを denpa の側へ通すことになり、
   **エージェントを別のマシンに増やす**という話 (下記) が成り立たなくなります
2. **解くのは選局ごとに1回で足ります。** 相乗りを捌いているのはエージェントで、
   同じチャンネルを録画・番組表・ロゴの3人が読んでも選局は1本です。denpa 側で
   解くと、**送られてきた3本をそれぞれ解く**ことになり、MULTI2 が3倍になります
3. **denpa が中身を触らずに済みます。** 録るものをそのまま書くだけでよく、
   「解けているか」を気にするのは受け取ったあとの検査だけで済みます

**それでも欲しくなる形が1つあります。** エージェントを2台に増やしたとき、
カードは片方にしかありません。そのときに要るのは「カードごと移す」ことではなく、
**ECM を投げて鍵を貰う口**です。ECM は 256 バイトほど、返るのは鍵だけなので、
これだけならネットワークを跨いでも安く、**MULTI2 は各エージェントの手元**に
残ります (重いのはこちら)。

さいわい libaribb25 の側も**カードは関数ポインタの表** (`B_CAS_CARD`) で、
`proc_ecm` だけ別のところへ投げる実装を差し込めます。**カードを持たない
エージェントが、持っているほうへ聞きにいく**という形にできて、いまの作りを
崩さずに後から足せます。要るようになってからで間に合います。

### エージェントは .NET (Native AOT) — **入りました**

**境界はもう引いてあります。** エージェントは中身を読まず、TSをそのまま流す。
読むのは denpa 側で、`src/lib/ts/` に PSI (NIT/SDT)・EIT・ロゴ・局の選り分けが
揃っています。チャンネルスキャンも「エージェントが順に選局して流す →
denpa が NIT/SDT を読む」の形です。

| | 誰が | 何を |
| --- | --- | --- |
| **エージェント** | 機材に触るところ | デバイスを開く・選局する・取り合いを裁く・B25 を解く → **バイト列を配る** |
| **denpa (TypeScript)** | 中身を分かるところ | PSI/SI・EIT・ロゴ・番組表・予約・録画・画面 |

**この境界のほうが言語より大事です。** ここを崩してエージェントに EIT の解析まで
持たせると、どちらの言語を選んでも同じものを2箇所に持つことになります。

そのうえで、**掴んだままにするには ioctl を直に叩く必要がある**ので、
bun では書けませんでした。以下は選んだときの理由で、そのまま入っています。

#### なぜ .NET か

**手が動く言語だから**です。1人で持つものなので、録画に失敗した夜中に直せるかどうかが
いちばん効きます。そのうえで、この用途で .NET が困らないことを確かめました。

- **P/Invoke で ioctl も libaribb25 も呼べます。** `[LibraryImport]` と
  `[StructLayout(LayoutKind.Sequential)]`、そして C# の関数ポインタ
  (`delegate* unmanaged<...>`) で、`dtv_properties` も `struct ptx_freq` も素直に組めます
- **Native AOT で1個の実行ファイルになります。** 別PCへ置くのに「まず何かを入れて
  ください」が要らない、という条件はこれで満たせます。**AOT は必須**で、
  これを外すと別PCの話が崩れます
- **速さは問題になりません。** チューナー4本でも 10 MB/s 程度で、`Span<byte>` と
  `ArrayPool<byte>` を使えば十分に収まります

#### Rust と比べて失うもの

- **`b25-sys` が無い。** Rust には[実機で今まさに解いている](#b25-の解除は-libaribb25)
  wrapper がありますが、.NET には無いので自分で書きます。ただし
  `libaribb25` の公開APIは **`create_arib_std_b25()` と関数ポインタの表**だけです
  (`put` / `get` / `set_b_cas_card` / `flush` …)。C# の関数ポインタで受ければ
  marshalling 無しで呼べるので、**1日ぶんの写経**で済む見込みです
- **GC がある。** ただし気をつけるのは読み取りの一本道だけで、188バイトごとに
  確保しない (`ArrayPool` / `Span` / pipelines) を守れば足ります

#### 逆に、思ったほど失わないもの

**Rust の安全性の利点は、ここでは C 相手ほど大きくありません。** .NET も安全な言語で、
危ないのは**どちらも同じ FFI の境目だけ**です。Rust で書いても `unsafe` を通るのは
ioctl と `libaribb25` の呼び出しで、.NET の P/Invoke と同じ場所です。

`Marshal.GetDelegateForFunctionPointer` は使いません (遅いうえ AOT で気を遣います)。
関数ポインタで直に呼びます。

#### 書き直しにはなりませんでした

移したのは取り合いの決まり・チャンネルの控え・HTTP の口だけです
(チャンネルスキャンは denpa へ移ったので、持って行くものがそもそも減りました)。
決まりは1つも変えていません。

移してみて出た違いは2つで、**どちらも適合テストが捕まえました。**

- **控えの並び順**。bun 版は種別ごとに並べ替えて書いていた
- **日本語の書き方**。`System.Text.Json` は既定で `\u30C6` に逃がすので、
  `channels.json` が人の目で読めなくなる。全角空白 (U+3000) だけは
  .NET のどの符号化器も逃がすので、そこは合わせていない

ついでに1つ直っています。**蹴られた相手に失敗を伝えられるようになりました** —
bun では送信中の本文を打ち切っても正常終了として届いてしまい、蹴られた録画が
尻切れのまま「録れた」ことになっていました。Kestrel は接続を壊せます
([architecture.md](architecture.md#選局は読み手が切るまで終わらない))。

**プロセスは分けます。** 「立てるものは denpa だけ」は*同じイメージに入っていて
denpa が面倒を見る*という意味で、**同じプロセスという意味ではありません**。
ioctl と復号は落ちるときに落ちるので、そこで画面や他の録画まで道連れにしません
(この判断は言語とは別で、どの言語で書いても同じ結論になります)。

### 通信は HTTP。ローカルは Unix ドメインソケット

**HTTP のところは既に入っています** (`/denpa/stream` が素のTSを chunked で流します)。
残っているのは Unix ドメインソケットで、いまは TCP だけです。

**先に言っておくと、遅延は伝送路にはありません。** 効いているのは選局の同期
(周波数を変えれば必ず要る) と、受け取った側のバッファです。ループバックや
Unix ソケットの往復は桁が3つ違います。**低遅延のためにやるべきことは「溜めないこと」**で、
どの protocol を選ぶかではありません。

そのうえで、いちばん退屈なものを選びます。

| | 何で | 中身 |
| --- | --- | --- |
| 制御 (選局・解放・状態) | HTTP + JSON | 小さい要求と応答 |
| 知らせ (掴んだ・離した・同期が外れた) | SSE | denpa は自分の画面でもう使っている |
| **TS** | HTTP の chunked | **素のTSだけ。何も包まない** |

**ローカルは Unix ドメインソケット、別PCは TCP。**同じ HTTP なので、
住所が変わるだけで denpa 側のコードは1本で済みます。bun の `fetch` は
`fetch(url, { unix })` でそのまま喋れます (Linux では abstract socket も可)。
.NET 側は Kestrel が Unix ソケットと TCP を**同時に**listen できます。

**denpa 側は今と同じ形のまま**です。`/denpa/stream` を `fetch` して `response.body` を
読んでいるところは、**宛先が変わるだけ**で構造を変えずに済みます。
`curl --unix-socket … > x.ts` で人手でも確かめられます。

低遅延のために守ること:

- **溜めない。** 数パケット届いたらそのまま流します。64KB 貯めてから送ると、
  それだけで 25ms 積み上がります (1本 2.5 MB/s)
- **TCP を使うときは `TCP_NODELAY`。** 小さい書き込みが Nagle で待たされます
- **TSの上に枠を被せない。** 既に188バイトで区切られているものに、
  さらに長さやメッセージの枠を付ける理由がありません

採らないもの:

| 案 | なぜ |
| --- | --- |
| gRPC | .NET 側は良いが bun 側が重い。**不透明なバイト列に protobuf の枠は何も足しません** |
| HTTP/2 | 流しっぱなしの1本にフロー制御の窓が増えるだけ。h1 の chunked のほうが素直 |
| 共有メモリ / リングバッファ | いちばん速いが、**ローカル専用**なので道が2本になる。10 MB/s のために背負う複雑さではない |
| 自前のバイナリ protocol | 覗けなくなるだけ。枠が要らないことは上のとおり |

**背圧の向きは用途で変えます。** 録画は**落としません** (詰まったら待たせる。
電波は二度と来ません)。視聴は**落として構いません** (遅れて届くコマより、
いまのコマのほうが価値がある)。同じ選局を両方が読んでいることがあるので、
**読み手ごとに決める**必要があります。

### エージェントは denpa に同梱。増やすときだけ足す

いまは2つのイメージ (`denpa` と `denpa-agent`) を並べています。

- **既定では denpa と同じイメージに入っていて、denpa が起こします。** チューナーが
  1台のマシンに刺さっているふつうの構成では、**設置するものは denpa だけ**。
  ただし**プロセスは分けます** ([上記](#エージェントは-net-native-aot--入りました))
- **別PCのチューナーを足したいときは、そのPCにエージェントだけ入れる。**
  denpa の設定に住所を足すと、チューナーが増えたものとして扱う
- 取り合いは**denpa が全体を見て決め**、エージェントは言われたチャンネルを
  掴んで流す。どのエージェントの何本目か、は denpa 側の帳簿になる

### 気をつけること

- **録画を落とさない。** ここまでの入れ替え (mirakc をやめるところ) は、
  選局の仕方を変えずに周りだけ動かしたので、壊れても番組表が古くなるだけでした。
  ここから先は**選局そのもの**を書き換えるので、失敗の出かたが変わります
- **答え合わせの相手がもう居ない。** mirakc が居るうちは、読んだ局・番組表を
  あちらと突き合わせられました。いまは実機で出た結果が唯一の正解です
  (エージェント同士は `agent/conformance.test.ts` で突き合わせられます)
- **[ライブ視聴](stream.md) と同じ土台**です。視聴・録画・番組表・ロゴが同じ
  取り合いの上に乗るので、設計はまとめて考えます

### ついでに手に入るもの: CM用のロゴを**録画の前に**覚える

いま `.lgd` (CM判定用のロゴ) を作っているのは**エンコードの最中**です。つまり
**その局の1本目は、自分自身から覚えたロゴで自分自身を判定します。** 実機で
いちばん弱い結果が出たのはまさにこれで、録画34の `.lgd` は 00:31 —
**その録画自身のエンコード中**に作られたものでした。

**もう順番をひっくり返せます** — 番組表集めが全チャンネルを定期的に開くように
なったので、そこに相乗りするだけで生TSが手に入ります (掴んだままにできれば
なお只になりますが、それを待つ必要はありません)。

- 局を1つ選んで**数分ぶんだけ生TSを取り、`logoframe` に覚えさせて捨てる**。
  録画は1本も要りません
- 開いている選局に**相乗り**できるので、チューナーは増えません
  (放送波のPNGロゴでやっている `logo.ride` と同じ手)
- **覚えられない局が事前に分かります。** いまは録画が1本まるごと無駄になってから
  「ロゴを当てられませんでした」と出て、そこで初めて範囲を教える口が出ます。
  先に分かれば、チューナー画面で**録る前に**囲ってもらえます

**PNGロゴと同じようには回せません。** あちらは CDT / DSM-CC を読むだけなので只ですが、
`.lgd` は**映像を復号してコマを見る**必要があります (MPEG-2 を数分ぶん)。
CPU を食うので、相乗りついでに全局へ、とはいきません。
**何分あれば覚えられるか** (`-logo-samples 600` をどれだけの尺から採れば足りるか) も
測っていません — 実機で確かめたのは28分の素材だけです。

## 実機で確かめられていないもの

- **mirakc をやめたあとの全体** — 番組表を自分で集めるところ、局を選り分けて録るところ。
  E2E は偽エージェントが組み立てた TS で通っているが、実際の放送で読んだことはない
- **.NET エージェントでの選局と録画。** 像は組んであり配備には出していない。
  実機で確かめたのは、チューナーの自動検出 (PT3 の4本を正しく判別した)、
  **掴んだままの選局** (地上波・BS とも同期し、TS が 100% の同期バイトで出た)、
  **B25 の復号** (掛かっているパケットが 87.8% → 0.1%)。**録画はまだ通していない**
- **`px4_drv` の chardev での選局。** 書いてはあるが、ここに chardev のデバイスが
  1つも無いので当てられていない (値は `px4_drv` と `recisdb` から取った)
- 実際の放送で ARIB の文字符号がどこまで読めるか (外字の取りこぼし)
- CM検出を「ロゴまで見る」で実際の放送に回したときの精度と所要時間
- ロゴを当てられなかった局に、画面から範囲を教える流れ
- `logoframe` がロゴを覚えるのに要る尺 (上記。28分では足りると分かっている)
- Mac の `denpa://` 登録 (アプレットの組み立てと `lsregister`)
