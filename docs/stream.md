# 放送波ストリーミングシステム 構成設計

> **映像・音声・字幕 (第1〜2段階) が入っています。** データ放送と低遅延の追い込みは
> まだ設計だけです。どこまで入っているかは [§4](#4-実装の順序) を見てください。
> [roadmap.md](roadmap.md) の「ライブ視聴の残り」に対応します。

最終更新: 2026-08-08

---

## 1. 前提

| 項目 | 内容 |
| --- | --- |
| デプロイ形態 | **セルフホスト（1ユーザー = 1サーバ）** |
| アプリ | SvelteKit 単一アプリ（配信・視聴の両方を担当） |
| 入力ソース | 放送波 MPEG-TS（ISDB-T / ISDB-S） |
| 目標コーデック | AV1 + Opus |
| 必須機能 | ARIB字幕、データ放送（双方向含む）、複数音声・映像ストリーム |
| 非機能要件 | 低遅延 |

セルフホスト前提であることから、以下は**設計上の考慮から外す**:

- NVRAM のマルチユーザー分離（受信機 = サーバ = ユーザーが 1:1:1 で対応するため）
- ユーザーごとの地域設定・リモコン設定の分離
- 通信系コンテンツのプロキシにおけるユーザー識別

### 設計上の中核

**メディアとメタデータは同じコンテナに載らない。** ARIB字幕（B24 PES）もデータ放送（DSM-CC カルーセル + PSI/SI）も、fMP4 / WebM には規格上入れられず、ffmpeg も GStreamer も扱えない。したがって:

> **サイドチャネル用の WebSocket を 1 本用意し、字幕とデータ放送を同じ経路に相乗りさせる。**

これは迂回路ではなく、本システムの主要な設計要素である。

### 字幕はサーバで絵にする

**ブラウザに B24 を渡さない。** サーバ側で libaribcaption に描かせ、**絵と時刻だけ**を送る。

放送に絵は流れてこない。乗っているのは文字と「どこに・どの大きさで・何色で・背景の箱つきで」という指定で、テレビはそれを見て毎回自分で描いている。`-sub_type bitmap` はその描画を libaribcaption にやらせたもので、**それが「放送どおりの字幕の絵」**になる。

この経路は**録画側で実装・実測済み**（[encode.md「字幕は PGS 1本だけ」](encode.md#字幕は-pgs-1本だけ)、`src/lib/server/subtitle.ts`）。live で変わるのは出口だけで、`.sup` に書く代わりに WebSocket へ流す。

| | サーバで描く（採用） | ブラウザで描く（aribb24.js） |
| --- | --- | --- |
| 外字 (DRCS) | そのまま絵になる | 実装依存 |
| 位置・背景の箱・点滅 | 放送どおり | 実装依存 |
| 録画との見た目 | **完全に同じ**（同じ描画系） | 別実装なので揃わない |
| 帯域 | 実測 **毎秒 8.3KB**（[§5.2](#52-字幕sub2video)） | 数百バイト／字幕 |
| サーバ負荷 | live 1本につき ffmpeg が**もう1プロセス** | なし |
| クライアント側の自由度 | 拡大は画像の拡大になる | 文字サイズを変えられる |
| 持つコード | 出口だけ（録画と共通） | 字幕ライブラリ1本 |

帯域は実測で**毎秒 8.3KB**（変わった枚だけ送ったとき。[§5.2](#52-字幕sub2video) に内訳）。映像の隣では誤差になる。出す時刻は[§5.4](#54-時刻同期)（**H.264 は届いたら出す**。AV1 だけ符号器が溜め込むぶん待たせる）。

### 送るのは PGS ではなくパレット PNG

録画側は同じ絵を PGS にしている。live でもそのまま送りたくなるが、**ブラウザに PGS の
デコーダが無い**。自分で書くことになるうえ、PGS は色を YCrCb 限定レンジでしか持てないので、
サーバで変換したものをクライアントで戻す往復が入る。あの変換は mkv に入れるための
制約であって、live には無い。

代わりに**パレット PNG (color type 3)** で送る。作りは PGS とほとんど同じで、
持っている部品もそのまま使える。

| | PGS そのまま | **パレット PNG** | RGBA PNG |
| --- | --- | --- | --- |
| 使い回せるもの | `quantize` + `rle` + セグメント組み立て | **`quantize` + PLTE/tRNS の書き出し** | チャンクの書き出しだけ |
| 色 | 256色 + **YCrCb の往復** | 256色（PLTE に RGB のまま入る。往復なし） | 無劣化 |
| 大きさ | 1枚 30KB 前後 | 同程度（8bpp + deflate） | やや大きい |
| クライアント | **PGS デコーダを自作** | `createImageBitmap()` | `createImageBitmap()` |

`quantize` は `src/lib/pgs.ts`、PLTE/tRNS の組み立ては `src/lib/ts/logo-palette.ts`
（ARIB ロゴ用に書いたもの）。deflate は `node:zlib`。実測で字幕は230色なので、
256色に落としても実質劣化しない。

**要するに PGS からセグメントの殻を外して PNG に着替えるだけ**で、サーバ側の再利用度は
PGS を送るのと変わらず、クライアントに書くコードが無くなる。

| エンコード | FFmpeg（将来 QSVEncC/NVEncC/VCEEncC） | — | CLI パイプラインで差し替え可能 |
| 字幕の描画 | xqq/libaribcaption | 127 | `-sub_type bitmap` + sub2video。録画側と同じ。denpa の ffmpeg は `--enable-libaribcaption` で組んである |
| データ放送抽出 | xtne6f/psisiarc | 19 | PSI/SI + カルーセルを .psc に圧縮 |
| データ放送描画 | otya128/web-bml | 246 | BMLブラウザ。サイドカーとして起動 |
| 再生 | MSE 直接 / Vanilagy/mediabunny | 6,846 | AV1+Opus fMP4 |
| WebRTC 化（任意） | bluenviron/mediamtx | 19,690 | AV1 over WebRTC / WHEP |

★は 2026-08-02 時点。日本の放送関連ツールはスター数が2桁だが**代替が存在しない**ため、数値で評価しないこと。

**TS 整形の `tsreadex` は入れかけて外した。** 挟む理由として挙げたものが、どれも
ffmpeg 単体で足りた（[§4](#tsreadex-は挟まない)）。

**mpegts.js と aribb24.js は使わない。** どちらも「H.264 + MPEG-TS をブラウザで直接再生し、
字幕も TS の中から拾う」構成のための部品で、fMP4 + サイドチャネルにすると出番が無くなる。
段階を踏むために一度その構成を通す案もあったが、**字幕の経路が録画側で先に完成した**ため、
捨てることになるコードを書く理由が無くなった。

## 4. 実装の順序

作るものは1つ。難所は「AV1 のリアルタイムエンコード」だけに絞れているので、そこだけ逃げ道を用意する。

1. **メディア経路** — `ffmpeg → fMP4 → WebSocket → MSE`。まず映像音声だけ出す — **入っています**
2. **字幕** — 2本目の ffmpeg を足してサイドチャネルへ流し、canvas に重ねる — **入っています**
3. **データ放送** — psisiarc → web-bml をサイドカーとして起動し、iframe で抱える
4. **低遅延の追い込み（任意）** — MediaMTX 経由で WebRTC/WHEP（0.2秒級）、または Media over QUIC

**コーデックは段階ではなく設定にする。** AV1 が回らない環境・Safari では H.264 + AAC に
切り替える。エンコーダとコンテナ以外は共通なので、字幕もデータ放送もそのまま動く。

### 入っているもの

| | |
| --- | --- |
| 画面 | `/live`。左に映像、右にチャンネル。**前回見ていた局から開く** |
| 焼き方 | **H.264 + AAC / AV1 + Opus を見ながら選べる**（[§5.1](#51-エンコード)）。`src/lib/server/live.ts` |
| 運び方 | WebSocket 1本。多重化の頭は [§5.3](#53-websocket-プロトコル) のまま |
| チューナー | 優先度 **9**。録画 (10) にだけ譲り、番組表もロゴもスキャンも蹴る |
| 相乗り | 同じ局を2人で見ても、チューナーも ffmpeg も1つ |
| 畳み方 | **見ている人が0になったら離す**。接続そのものが在席の印 |

**相乗りの単位は局とコマ数と音声。** 1本の物理チャンネルに複数の局が乗っていて、
ffmpeg には局を名指しさせている（下記）ので、出てくる絵が局ごとに違う。
コマ数も同じで、国内アニメを見ている人と実写を見ている人では違う。音声も同じで、
二カ国語を主音声で見ている人と副音声で見ている人は別のものを焼いている。
チューナーはエージェント側で相乗りになるので、増えるのは ffmpeg だけ。

### 多重音声はサーバで1本に決める

**「多重音声」と呼ばれるものは中身の違う2通りある。** 見ている人にとってはどちらも
「音声を選ぶ」1つの操作でしかないので、**平らに並べて1つの一覧に見せる**
（`arib.audioTracks`）。

| | 中身 | 分け方 |
| --- | --- | --- |
| デュアルモノ | 音声は**1本**。左に主音声・右に副音声（二カ国語・解説放送） | `-af pan=stereo\|c0=c0\|c1=c0`（副音声は `c1`） |
| 複数の音声 | 音声そのものが**2本以上** | `-map 0:p:<局>:a:<何本目>` |

デュアルモノは1本から3つ（主・副・主+副）出てくる。テレビの「音声切換」と同じ3択。

**選ぶのはサーバ側。** 音声を全部まとめて送ってブラウザで切り替える手もあるが、
MSE は1つの器に複数の音声を入れた fMP4 を、ブラウザによっては切り替えられない
（`audioTracks` の実装がまちまち）。焼くときに1本に決めてしまえば、どのブラウザでも
同じように鳴る。代償は**選び直しが焼き直しになる**こと — チャンネルは変わらないので
チューナーは掴んだままで、かかるのは焼き始めのぶんだけ。

**選べるものは繋いだあとでないと分からない。** 二カ国語の映画が終わればステレオに
戻るので、局の一覧からは決められない。選局のたびに現物を `tuned` に載せて送る。
覚えていた合言葉が選べなくなっていたら先頭に落とす（`arib.pickTrack`）— 落とさないと
番組が変わった瞬間に音が出なくなる。

### 追っかけ再生とライブは別物

止めて見ていたり、帯を戻したりして**わざと遅れて見ている**状態を、ライブと分けて持つ。

| | ライブ | 追っかけ |
| --- | --- | --- |
| 大きく離れたら | **跳んで詰める**（別のタブから戻ったとき） | **跳ばない**（見ようとしていた場面が飛ぶ） |
| 速さ | 自動（1.05倍まで） | **選べる**（1 / 1.25 / 1.5 / 2倍） |
| 追いついたら | — | **自分でライブに戻る** |

**分けていなかった頃は、止めて再開すると勝手に放送の今へ跳んでいた。**
`pacing` が「大きく離れた」としか見ておらず、それが「別のタブから戻ってきた」なのか
「わざと遅れて見ている」なのか区別できていなかった。8秒より長く止めると戻れないので、
「止めた所から見られる」と謳っておきながら実際には効いていない。

**追いついたら自分で戻すのが要る。** 戻さずに選ばれた速さのまま進むと放送を追い越し、
溜まりを使い切って止まる。実機で 15.8 秒遅れから2倍で追わせると、14.9 秒で追いついて
速さが 1 に戻った。

### 開いてから絵が出るまでの内訳

実機（PT3 + `earth_pt3`）で割った。**チューナーが温まっていれば ≈0.89 秒**、
冷えていれば頭に選局の 0.66 秒が付く。

| | |
| --- | --- |
| 画面が動き出して札を取り、WebSocket が繋がるまで | 160ms |
| ffmpeg の立ち上がり（固定） | 530ms |
| 放送の I フレーム待ち | **0〜501ms**（GOP はちょうど 501ms） |
| **貯めてから始める**（`pacing.ts` の `FLOOR`） | **200ms**（0.4秒だったのを半分に） |
| MSE に入れて1枚映るまで | 40ms |

**`FLOOR` はこちらの都合で動かせる唯一のところ。** 再生を始める条件は
「貯まった尺 ≧ 貯める量」で、電波は実時間で届くのだから、0.4 秒貯めるには
0.4 秒かかる。0.2 秒 = 塊4つぶん（サーバは 0.05 秒ずつ出す）まで下げた。
**足りずに止まったら 0.6 ずつ増える**ので、荒れる経路では自分で伸びる — 迷ったら
小さいほうから始めてよい。

冷えているときの選局 0.66 秒の中身：

| | |
| --- | --- |
| 頼んでから選局の ioctl を出すまで | 42ms |
| **復調器がロックするまで** | **320ms**（実測 319〜323ms。ISDB-T の OFDM フレームは約 205ms） |
| ドライバが TS を出しはじめるまで | 0〜7ms |
| ロックしてから denpa の1バイト目まで | 240ms（PAT 60ms → PMT 110ms → **ECM 50〜250ms** → カードの往復） |

**削れたのは 160ms だけだった。** 画面が繋いでくる前にサーバ側で焼きはじめる
（`server/live.ts` の `warm`）と、その 160ms が ffmpeg の 530ms と重なる。開く局は
ページを組む時点で決まっているので、待たずに始められる。

> **PSI を先に流す手は外した。** ffmpeg は入口で PAT と PMT を待つので、前に開いた
> ときの PAT/PMT を取っておいて先に流せば、選局を待つ 0.66 秒に入口の仕事を重ねられる。
> 単体で測ると効いていた（888ms → 707ms、ばらつきも 342ms → 77ms）。
>
> **実機では切り替えが壊れた。** 電波が来るより先に ffmpeg が入口を読み終えてしまい、
> `-map 0:p:<局>:v:0` がその時点の情報で解決できずに**そのまま終了する**：
>
> ```
> Failed to set value '0:p:24632:v:0' for option 'map': Invalid argument
> Error opening output files: Invalid argument
> ```
>
> 測ったときは選局済みで、呼び水の直後に本物が来ていた。**効くはずの場面
> （選局に 0.66 秒かかるとき）でだけ壊れる**ので、測っているときには見えなかった。

> **同じ落ち方が、先出しとは無関係にも起きていた。** 局が3つ相乗りしている TS
> （実機の tvk / T15。tvk1・2・3 + ワンセグ + データで、局ごとに14本以上の
> ストリームがある）では、`-probesize 400000` が足りず `-map 0:p:24632:v:0` を
> 解決できないまま ffmpeg が降りる。**渡す前に1局へ絞って直した**（下の
> 「渡す前に1局へ絞る」）。

### 渡す前に1局へ絞る

ffmpeg は名指しした局を `-probesize` のぶん読む間に見つけられなければ、
**そのまま終了する**。わざと probesize を下げて T15 で測ったもの（3回ずつ）:

| probesize | 丸ごと渡す | 1局に絞る |
| --- | --- | --- |
| 20KB | **0/3 通る** | 3/3 |
| 50KB | **0/3 通る** | 3/3 |
| 120KB | **1/3 通る** | 3/3 |
| 400KB | 3/3 | 3/3 |

**絞れば 20KB でも通る。** 録画と同じ `ServiceFilter` を通すだけで、ffmpeg が
受け取るのは局が1つだけの TS になる。局を探す仕事が消えるので `-probesize` は
**400KB → 20KB**。字幕側も同じ。

そこまで下げてよいかは、6回ずつ測って決めた:

| probesize | 最短 | 中央 | 通った |
| --- | --- | --- | --- |
| 100KB | 474ms | 839ms | 6/6 |
| **20KB** | **441ms** | 752ms | 6/6 |

**中央値の差はばらつき**（放送の GOP 待ち 0〜501ms）で、**最短どうしの 33ms が
固定の費用**。絞った TS の PAT は最初のパケットから入っているので、探すものが無い。

> **削ったぶん、コマ数は読み切れなくなる。** ffmpeg は時間の刻み（90kHz）から
> でたらめな値を起こすことがあり、x264 は黙って受けるが **SVT-AV1 は突っぱねる**
> （`The maximum allowed frame rate is 240 fps`）。実機で 20KB のまま AV1 を選ぶと
> **0/3**、上限（`-fpsmax`）を付けると **3/3** 通った。
>
> **固定（`-r`）ではなく上限にする。** 固定すると、放送が本当に 59.94p だったとき
> （720p の局）にコマを落とす。上限なら、まともな値のときは何も起きない。

名指し（`0:p:<局>`）はそのまま残す。絞ったものに万一違う局が入っていたら、
**黙って別の局を映すより、そこで落ちるほうがいい**。

**量はほとんど減らない。** 実測は tvk で 17.6 → 16.8 Mbit/s、日テレで
17.3 → 14.5 Mbit/s。相乗りしている局は**同じ ES を指している**ことが多いので
（tvk1/2/3 は同じ中継を流している）、落ちるのは他局ぶんの表と詰め物だけ。
狙いは量ではなく、**ffmpeg に局を探させないこと**。

**黙って黒くなることもなくなった**。ffmpeg が降りたらその場で
「映像を出せませんでした」を出す（下の「焼けなくなったら、その場で言う」）。

### 焼けなくなったら、その場で言う

ffmpeg が降りても何も伝えていなかった頃は、画面には**前の絵が貼られたまま6秒たって
黒くなる**だけだった（`live-player.svelte.ts` の `HOLD_MOST`）。見た目は
「切り替えに6秒かかった」で、実際には失敗しているのに、そうとは分からない出方をする。

2つ直した。

- **終わりを ffmpeg の終了で見る。** 汲み出しは相手が死ねばすぐ終わるが、
  **流し込みは終わらない**（書き込み先が閉じても例外にならないことがあり、放送は
  止まらないので回り続ける）。3つ揃うのを待っていると、死んだことに永久に気づかない
- **畳んだセッションを掴んだままにしない。** 繋いでいる側は同じものを指したままなので、
  同じ局を選び直しても「もう見ている」と見なされて何も起きず、**「やり直す」を
  押しても直らなかった**

残りは全部、放送か機材か ARIB の都合：

- **ロックの 320ms はチップの物理時間。** ドライバを替えても同じ
  （`dvb_override_tune_delay` を 1ms にして試すと、DVB core が同期の途中で
  周波数を振り直すぶん **451ms に悪化**した。あの値は「諦めるまでの猶予」で、
  ロックの検出間隔ではない。検出はこちらが 10ms 間隔で直に読んでいる）
- **ロック後の 240ms はスクランブル解除。** ECM が来るまで鍵が作れない
- **I フレーム待ちは放送の GOP。** MPEG-2 は I フレームからしか復号を始められない
- **符号器は道の上に居ない。** `-tune zerolatency` は B フレームも先読みも作らない。
  インタレ解除・音声・塊の細かさを外しても縮まなかった（実測）

器を作り直すと `<video>` は何も映さなくなるので、そのままだとその間ずっと真っ黒になる。

器を捨てる前に1枚だけ canvas へ写して重ね、**次の絵が実際に出た時点で剥がす**
（`requestVideoFrameCallback`。`play()` が返っただけではまだ何も映っていない）。
待ち時間そのものは変わらないが、黒い画面を見せずに済む。絵は止まって見えるが、
それは正しい — 実際に止まっている。

貼りっぱなしを避ける上限（6秒）を置く。**壊れているのに動いて見えるのがいちばん悪い。**

**まず H.264 + AAC で通した。** 狙いは AV1 + Opus だが、実機に HW エンコーダが
無く（`ffmpeg -hwaccels` が空）、CPU も AVX-512 を持たない世代（Xeon E5 v4）なので
ソフトウェアの AV1 は賭けだった。**難所を1つに絞る**ため、確実に出るほうから始めた。
**いまは両方入っていて、見ながら選べます**（[§5.1](#51-エンコード)）。

### `tsreadex` は挟まない

一度は入れかけたが、**挟む理由として挙げたものが、どれも ffmpeg 単体で足りた**。

| 欲しかったもの | 結論 |
| --- | --- |
| デュアルモノ分離 | ffmpeg で足りる。**録画と同じ見分け方**（番組表の音声情報）で、選ばれた側を両耳へ配る（上記）。録画は左右を2トラックに分けるが、ライブは器が1つなので片方を採る |
| 局の選び分け | ffmpeg で足りる。`-map 0:p:<局>:v:0`。実機で確認済み |
| 音声・字幕が消えたときに無音を挿す | tsreadex にしかできない。ただし**実害を確認していない** |
| `aac: Input buffer exhausted` | **そもそも直らない**。壊れた AAC フレームの修復は tsreadex の仕事ではない |

イメージに1つ足す代償に対して、いま得られるものが最後の2行しかない。**3行目の実害を
実際に踏んだら**入れる。

### 局は名指しで選ぶ

**1本の物理チャンネルに複数の局が乗っている。** `-map 0:v:0` は「最初に見つけた映像」
でしかないので、MX2 を選んでも MX1 の絵が出うる。実機の T26 を調べると局が4つ
（Eテレ1/2/3 と**ワンセグ**）並んでいて、ワンセグは 320x180 の H.264 — それを掴む目まである。

`-map 0:p:<局>:v:0` なら選んだ局の中から選ぶ。選局の指示に局まで載せているのは
このためでもある（コマ数の判定と共用）。

### 入口が1つ増えている

**bun の `node:http` は WebSocket の握手ができない。** `upgrade` は上がるのに、
渡される socket に書いても相手に1バイトも届かない（`write()` は true を返し、
コールバックも成功と言う。`_handle` が空）。adapter-node はその上に居るので、
そのままでは通らない。

`svelte-adapter-bun`（[Bun 公式が案内している](https://bun.com/guides/ecosystem/sveltekit)）
にも替えてみたが、**今の SvelteKit では動かない**。あちらは kit の生成物を正規表現で
4か所書き換えて `websocket` フックを挿し込む作りで、`get_hooks` が別チャンクへ
出るようになったため2か所が当たらず、`Bun.serve` に `websocket` が渡らない
（`To enable websocket support, set the "websocket" object` で 500）。

そこで **`Bun.serve` を前に置き、WebSocket だけそこで受ける**（`server.js`）。

```text
ブラウザ ──→ Bun.serve (公開ポート)
                ├ /api/live/socket → WebSocket をここで受ける
                └ それ以外          → 127.0.0.1 の adapter-node へ中継
```

**取るのは WebSocket だけ。** 録画の配信（Range 要求）も認証も SSE も、Pod 入れ替え時に
録画が終わるまで居座る仕掛けも adapter-node に乗っているので、触らないのがいちばん安い。
`Host` はそのまま渡す — 書き換わると CSRF 判定が自分の origin と食い違い、フォーム送信が
全部弾かれる（denpa は名前を2つ持っていて `ORIGIN` で固定できない）。

**開発サーバ（`bun run dev`）ではライブが繋がらない。** vite が持つのは `node:http` で、
上の理由で握手できないため。確かめるときは `bun run build && bun ./server.js` を使う。

### 繋ぐときの認証

**ブラウザは WebSocket の握手に `Authorization` を付けてくれない。** ベーシック認証で
守っている denpa では、そのままだとチューナーを掴む口が素通しになる。

画面が先に `POST /api/live/ticket` で**使い捨ての札**を取り、それを URL に付けて繋ぐ。
札の発行は普通の HTTP なので、ベーシック認証も OIDC も信頼した網もそのまま効く。
**1回使ったら消す**（URL は履歴にもログにも残るため）。寿命は30秒。

## 5. 実装詳細

### 5.1 エンコード

**いま回している形は `src/lib/server/live.ts` の `encodeArgs` にあります。** 1本の
ffmpeg が映像と音声を1つの pipe へ多重化し、`Fmp4Splitter` が `moof`+`mdat` ごとに
割って WebSocket へ流します。

```bash
ffmpeg -fflags nobuffer -probesize <小さく> -copyts -i pipe:0 \
    -vf <インタレ解除> \
    -map 0:p:<局>:v:0 -fpsmax <上限> <映像の焼き方> \
    -map 0:p:<局>:a:<何本目> [-af pan=...] <音声の焼き方> \
    -f mp4 -movflags +empty_moov+default_base_moof \
    -frag_duration 50000 -flush_packets 1 pipe:1
```

**値は書きません。形だけです。** 実測した値と理由は `encodeArgs` の説明にあり、
**写すと必ず片方が古くなります** — 実際ここには `-frag_duration` が古いまま残って
いたことがあり、直したあとも `-probesize` と `-preset` と音声の量が同じように
古くなっていました。なぜこの形かは [§4](#入っているもの) にあります。

- **`-copyts` は残す。** 受け側は使いません（fMP4 は 0 から始まるので物差しが違う）が、
  外すと**サーバ側で映像と字幕の出口を突き合わせて測れなくなります**。字幕を待たせる
  量（[§5.4](#54-時刻同期)）はそうやって測った値です
- クライアント側の SourceBuffer は `segments`（既定）で使う。`sequence` は
  「届いた順に詰める」動きなので、1つ取りこぼすと以降ずっとずれる。
  再生位置の面倒（貯めてから出す・離れたら速める）は `src/lib/ts/pacing.ts`

**将来トラックごとに pipe を分けるなら**、`-movflags +frag_every_frame` に戻せます。
1本に多重化している間は使えません（[§4](#入っているもの)）。複数映像も
そのときの話で、いまは映像1本・音声1本に決め打っています。

#### 焼き方は見ながら選べる

画面の操作列から **H.264 / AV1** を選び直せる（`LiveCodec`）。音声と同じで、選び直すと
焼き直しになる（器から作り直し）が、チャンネルは変わらないのでチューナーは掴んだまま。
**局を変えても引き継ぐ** — 絵の中身ではなく「その端末で出るか」の話なので。

実機（Xeon E5-2696 v4 / 44スレッド / HW エンコーダ無し）で、同じ電波を 40 秒ずつ
通した実測。1080i を解いて 60 コマ/秒という、いちばん重い形:

| | 1バイト目 | 焼けた尺 / 実時間 |
| --- | --- | --- |
| x264 veryfast | 729ms | 38.5秒 / 41秒 |
| **AV1 (SVT preset 12)** | 1177ms | **39.1秒 / 41秒** |

**落ちこぼれない。** 設計では「ソフトウェアの AV1 は厳しい」としていたが、
コア数で間に合った。立ち上がりが 0.45 秒ぶん遅いのが代償。
既定は H.264 のまま — **どの端末でも出る**ほうから始める。

**量については、まだ何とも言えない。** どちらも品質を指定して焼いている
（ビットレートを決めていない）ので、出てくる量は場面で動く。実測も揃わなかった:

| | x264 | AV1 |
| --- | --- | --- |
| ある40秒 | 3.3 Mbit/s | **2.8 Mbit/s**（15%小さい） |
| 別の25秒 | 11.6 Mbit/s | 11.4 Mbit/s（ほぼ同じ） |

**音声は AV1 のとき Opus、H.264 は AAC。どちらも 256k** — 元の放送（AAC 256kbps）
に合わせた値で、録画側も前から `libopus -b:a 256k`。

#### 役割を分ける — H.264 は「速く」、AV1 は「小さく」

H.264 は**量を捨てて速さを採る**（`-preset ultrafast`、画質は既定のまま）。
実測（6回ずつ）。ばらつきは放送の GOP 待ち（0〜501ms）なので、**短いほうの2つ**を見る:

| | 最短 | 2番目 | 量 |
| --- | --- | --- | --- |
| veryfast 既定 | 438ms | 535ms | 2.5 Mbit/s |
| **ultrafast 既定** | **386ms** | **429ms** | 8.2 Mbit/s |
| ultrafast + crf 20 | 524ms | 584ms | 10.7 Mbit/s |
| ultrafast + crf 18 | 478ms | 511ms | 14.6 Mbit/s |
| ultrafast + crf 14 | 586ms | — | 35.9 Mbit/s |
| ultrafast + 無劣化（`-qp 0`） | 643ms | — | 235.7 Mbit/s |

**画質を上げると必ず遅くなる。** 最初の1枚が太り、書き出すのに時間がかかるため。
`-crf` を付けないのが最速で、**出てくる絵は今までと同じ**（同じ crf 23）。
増えるのは量だけ — 同じ画質を `ultrafast` で出すと 3 倍になる。

8.2 Mbit/s は**宅内向けの値**。宅外から見るときは AV1 を選ぶ。

> **戻れる幅はバイト数でも切る。** 5分（`KEEP`）は「毎秒 3Mbit なら 110MB」の
> つもりの値だった。8.2 Mbit/s で5分持つと **300MB** になり、`appendBuffer` が
> `QuotaExceededError` で落ちて**そこから絵が出なくなる**。受け取っている速さから
> 120MB に収まる長さを出して、時間と小さいほうで切る（`live-player.svelte.ts`）。

`lookahead=0` が要る。SVT-AV1 は既定で先を読むぶん貯めるので、付けないとその貯めが
そのまま遅れになる。preset 12 を採る（13 は目に見えて粗く、10 は間に合わない）。

> **付けてもまだ溜め込む。** 電波が届いてから mp4 の塊が出るまで、H.264 が 0.24〜0.49 秒
> なのに対し **AV1 は 1.1〜1.5 秒**（実測。60コマのほうが枚数で捌けるぶん短い）。
> 低遅延指定（`pred-struct=1`）は**実時間に間に合わなくなる** — 出口が 6秒 → 22秒 と
> 離れていった。**AV1 を選ぶと放送の今から1秒ぶん離れる**ので、切り替えにもそう書いてある。

**受け取れない端末では H.264 に戻す。** `MediaSource.isTypeSupported` が false なら
その場で戻して、戻した理由を画面に出す。黙って別の形にすると、なぜ切り替えが
効かないのか分からない。

HW エンコーダのある機材なら `av1_nvenc`（RTX40以降）/ `av1_qsv`（Arc・Meteor Lake 以降）/
`av1_amf`（RDNA3以降）に載せ替えられる。

### 5.2 字幕（sub2video）

映像を作らない ffmpeg をもう1本、同じチャンネルに当てる（`src/lib/server/captions.ts`）。

```bash
ffmpeg -copyts -sub_type bitmap -canvas_size 1920x1080 \
    -font 'Rounded M+ 1m for ARIB' -fflags nobuffer -probesize 100000 -i pipe:0 \
    -filter_complex '[0:p:<局>:s:0]null[v]' -map '[v]' -fps_mode passthrough \
    -f image2pipe -c:v png -pix_fmt rgba pipe:1
```

- 字幕をフィルタの入力にすると、字幕1枚ごとに映像フレームになる（sub2video）。
  **通す先は何でもよい**ので `null` にしてある — 通すこと自体が目的
- **標準エラーには何も喋らせない。** ここが `showinfo` だった頃の失敗は下の
  「別の口と組にしない」
- `-canvas_size` は必須。指定が無いと libaribcaption は 1440x1080 (PROFILE_A) とみなすので、
  1920x1080 の放送では字幕だけ横に伸びる
- **局を名指しする。** 映像と同じ理由（1本の物理チャンネルに複数の局が乗っている）

#### PNG は ffmpeg に組ませる

設計では生の RGBA を受け取って、denpa が切り抜き・256色化・パレット PNG の組み立てまで
やることにしていた。**実機で測ったら、ffmpeg に PNG まで畳ませるほうが速かった。**
同じ TS 30秒ぶん（字幕49枚）を通したときの実測:

| | 時間 | 出た量 | 1枚 |
| --- | --- | --- | --- |
| 生の RGBA | 1.94秒 | 406 MB | 8.29 MB |
| **PNG** | **1.05秒** | 1.76 MB | 36 KB |
| 256色 PNG | 4.30秒 | 0.94 MB | 19 KB |

**生のほうが遅いのは、書く量が桁違いだから**（毎秒 13MB をパイプに流す）。256色に落とせば
半分になるが、そのために CPU を4倍払う。denpa 側の切り抜き・色数落とし・PNG 組み立ては、
まるごと要らなくなった（`crop` / `quantize` / `logo-palette` を使う話は無し）。

送るのは画面まるごとの PNG で、受け側は映像と同じ枠に敷いて引き伸ばすだけ。
**切り抜きは要らなかった** — PGS には1秒あたりに送れる量の決まりがあるので録画側では
切っているが、こちらにその縛りは無い。

#### 変わったときだけ送る

**sub2video は同じ絵を何度も出す。** 実機で数えると毎分98枚出てくるが、**中身が
変わっているのは18回だけ**（残り8割は出し直し）。そのまま流すと毎秒 57KB、変わった
ときだけなら**毎秒 8.3KB**。宅外から見ることを考えると落とす価値がある。

空の枚（全部透明）も**そのまま送る**。重ねれば消えるので、「消す」に置き換える必要が無い。
1枚 10.6KB、実機の頻度（毎分9回くらい）で**毎秒 1.6KB** 増えるが、下の理由でその価値がある。

#### 別の口と組にしない

以前は `showinfo` に時刻と「空かどうか」（`mean:` の最後がアルファの平均）を標準エラーへ
喋らせ、**その行と標準出力の PNG を来た順に1対1で組にして**いた。

**数が合わない。** 実機の日テレで70秒測ると:

| | |
| --- | --- |
| 出てきた PNG | **77枚** |
| showinfo の行 | **79行** |

余った2行のぶんだけ**以降ずっと1つずれる**（一度ずれたら戻らない）。フィルタを通った枚が
そのまま出てくるとは限らないため（同じ時刻の枚は多重化のところで落ちる）で、
**別々の口から来るものを位置で突き合わせている限り、ずれ得る。**

ずれると、字幕が出た枚に1つ前の「空」が当たって**消す**に化け、その字幕は次の出し直しまで
出ない。**字幕が1秒ほど遅れて出て、消えるのも遅れる** — 「字幕が遅れて固まって出る」という
報告そのままの出方をする。

いまは PNG だけを見る。**ずれ得ない作りのほうが、毎秒 1.6KB より価値がある。**
外したぶん ffmpeg の標準エラーも静かになった（40秒で 383行 → 109行）。

#### 局までで分ける

字幕は局で決まるので、**焼き方（コマ数・音声）では分けない。** 音声を選び直しても
字幕は途切れず、同じ局を別の音声で見ている2人は同じ ffmpeg を共有する。
チューナーはエージェント側で相乗りになるので、増えるのは ffmpeg 1本と、
**TS がもう一度 HTTP を渡ること**だけ（ロゴ集めと同じ取引 — [agent.md](agent.md)）。

実費は **CPU 3.5%**。映像を焼いているほう（350〜470%）の隣では誤差になる。

> **字幕が1枚も来ない番組がある。** 絵は描くものがあったときだけ出るので、本編に字幕が
> 無ければ0枚になる（録画側の実測でも同じ）。何も来ないことは異常ではない。
> 画面は**来ていないときは字幕ボタンを出さない** — 押しても何も起きない操作を並べない。

### 5.3 WebSocket プロトコル

単一接続で全チャネルを多重化する。

```
[1 byte: channel][8 bytes: PTS (90kHz, BE)][payload...]

channel:
  0x00  video init segment (ftyp + moov)
  0x01  video media  (moof + mdat)
  0x10  audio init segment
  0x11  audio media
  0x20  字幕の絵     [2:x][2:y][2:w][2:h][PNG...]
  0x21  字幕を消す   (中身なし) ※いまサーバは送らない
  0x30  PSI/SI + データカルーセル (.psc chunk)
  0x40  制御 (チャンネル切替、EPG更新通知 等)
```

- init セグメントは接続直後に必ず送る（再送用にサーバ側で保持）
- MSE はバイト列をそのまま `appendBuffer()` に投げられるため、映像音声のパースは不要
- 字幕の座標は `-canvas_size` の座標系。表示側の拡大率に合わせて canvas を伸ばす
- **字幕にいつ出すかは添えない。頭の PTS も使わない**（0 で置く）。合わせ方は
  [§5.4](#54-時刻同期)。待たせる量は選局のときに制御チャネルの `tuned` で伝える
- 途中から入ってきた視聴者のために、**いま出ている字幕はサーバが1枚だけ保持して再送する**

### 5.4 時刻同期

| 対象 | 方法 |
| --- | --- |
| 映像・音声 | fMP4 の timescale で自動的に整合 |
| 字幕 | **時刻では合わせない。いま映っている絵に、決まった量だけ足して置く** |
| データ放送 | カルーセルは時刻同期不要（PMT/TOT/EIT の更新に追従） |

**絶対の時刻で合わせる道は2回外した。** どちらも「こちらの都合で動く量」に頼っていたのが
間違いだった。

| 使った基準 | 実測のずれ |
| --- | --- |
| mp4 の 0（＝焼かれた1コマ目のつもり） | **2.4秒**。多重化器が 0 に合わせるのは probe の間に溜まった**音声** |
| 焼いている絵の時刻（映像側の `showinfo`） | **5秒**。フィルタは符号器より先を走る |
| 字幕側の `showinfo` が言う放送時刻 | **1秒ほど遅れる**。行と絵の数が合わず、組がずれる（[§5.2](#52-字幕sub2video)） |

**H.264 は待たせません。** 字幕が届いたときには、その字幕が属する映像も**もう届いて
います**。放送は字幕も映像も前もって送りますが（字幕は描く手間ぶん、映像は復号器の溜め
ぶん）、映像を焼いて包む手間がそれを食うので、差し引きで待ちは残りません。

**AV1 だけ待たせます。** SVT-AV1 が溜め込むぶん映像だけが遅れて届くためで、その差だけ
待たせます。値は `server/live.ts` の `captionLead`（写すと必ず片方が古くなる。
[§5.1](#51-エンコード) と同じ扱い）。

#### 待たせる量も2回外しました

**こちらは値ではなく、見方の間違いです。**

| | 何を見落としたか | 出た症状 |
| --- | --- | --- |
| 1回目 | **映像も先送りされている**ことを忘れ、字幕の先回りだけを見た | 0.5 秒待たせ、字幕が遅れた |
| 2回目 | 両方の差は採ったが、**焼く手間がそれを食う**ことを数え落とした | 0.42 秒待たせ、まだ遅れた |
| 3回目 | 待たせる量は 0 にしたが、**置く先を「届いている映像の端」にしていた** | 貯めているぶん（0.2 秒）遅れた |

1回目で「4局とも差は 7ms に収まる」と見えたのは**確かめになっていませんでした** —
字幕と映像の先回りは局ごとに同じ方向へ動くので、片方だけ見ても揃って見えます。

**測って詰めることはできませんでした。** 焼いた mp4 の中身がどの放送時刻に当たるかは
多重化器が握っていて外から見えず、別々に起こした ffmpeg は焼き始めの鍵フレームが
0〜0.5 秒ずれます。装置を5通り作って -60〜+450ms とばらけ、同じ局を2回測って 150ms
動きました。**決めたのは画面を見た人です** — 0 / 0.2 / 0.45 秒を出し比べて 0 が
いちばん合いました。局ごとに数える仕掛けは、そういうわけで消してあります。

**合わせる先は「いま映っている絵」**（再生位置）。届いた字幕は、その時点で映っている絵に
属しています。**「いちばん新しく届いている映像」（`buffered.end`）に置いていた頃は、
貯めているぶんだけ遅れて出ていました**（実測 0.2 秒）。あちらは「字幕の映像はまだ届いて
いない」という読みに立った置き方で、その読みが違いました。貯める量は宅外だと伸びるので、
遅れもそのぶん伸びます（`ts/captions.ts` の `captionAt`）。

**貼り直すのは、映した1枚ごと**（`live-player` の `follow`）。届いた塊に相乗りして
いた頃は 0.05 秒刻みでしか貼り直さず、**遅れる方向にだけ** 0〜50ms ずれていた。

**そのため映像側に `showinfo` は要らず**、送るものにも補正値は乗らない。

### 5.5 放送そのまま（MPEG-2）は出せない

**ブラウザに MPEG-2 の復号器が無い。** Chromium 151 で実際に聞いた結果:

| 聞き方 | `mp2v` / `mpeg2video` | `avc1` | `av01` | `vp09` | AAC |
| --- | --- | --- | --- | --- | --- |
| `MediaSource.isTypeSupported` | **×** | ○ | ○ | ○ | ○ |
| `VideoDecoder.isConfigSupported` | **×** | ○ | ○ | ○ | ○ |

（`video/mp2t` そのものは ○ だが、これは**中身が H.264 の TS** の話。放送の
MPEG-2 を入れても出ない）

つまり「焼かずにそのまま送る」を画面で出すには、**WASM で復号器を持ち込む**しかない
（libmpeg2 相当。音声の AAC はブラウザにあるのでそのまま使える）。得るものは大きい —
ffmpeg の立ち上がり 0.5〜0.7 秒が丸ごと消え、サーバの CPU も 350〜470% からほぼ 0 に
なる。**遅延も、焼くのに掛かっているぶん（電波が届いてから塊が出るまでの 0.24〜0.49 秒。
[§5.1](#51-エンコード)）が丸ごと落ちる** — 残るのは受け側の貯め（`ts/pacing.ts` の
`FLOOR` = 0.2 秒）だけになる。**TVTest 並みに手が届くのはこの道だけ。**

払うものも大きい:

- **帯域が約3倍。** 1局に絞った生の TS は実測 14.5〜16.8 Mbit/s、いま焼いているものは
  2.8〜7 Mbit/s。宅外から見ることを考えると、ここがいちばん重い
- 端末の CPU と電池（特に携帯）
- **MSE をやめることになる。** 貯め方・追っかけ再生・5分戻れる仕組みは全部 MSE の
  `buffered` に乗っている。自前の復号器だと、時刻合わせも溜め方も巻き戻しも書き直し。
  1080i の解除もシェーダで自前になり、いまの `bwdif` より落ちる

やるなら **LAN のときだけ生、宅外は焼く**という分け方になる（`TRUSTED_NETWORKS` で
既に見分けている）。**まだ入っていない。**

### 5.6 データ放送の統合

web-bml は Node.js サーバ + ブラウザクライアント構成（既定ポート 23234）。
**サイドカーとして起動し、iframe で抱えるのが最も低コスト。**

セルフホスト前提なので、NVRAM は web-bml の既定実装（サーバローカル保存）をそのまま使用する。

### 5.7 双方向（通信系コンテンツ）プロキシ

放送局の通信系サーバは受信機の専用ネットワークスタックを前提としており、CORS ヘッダを返さない。
そのため **SvelteKit サーバが中継する**。

```
/api/bml/proxy
  ├─ 許可ホストのホワイトリスト（PMT/AITから得た正規ドメインのみ）
  ├─ タイムアウト・レスポンスサイズ上限
  ├─ リクエストログ（デバッグ用）
  └─ 既定は無効。設定で明示的に有効化する
```

**既定オフとすること。** web-bml 系の実装も同じ方針を取っている
（TVTDataBroadcastingWV2: 「通信機能は既定では無効であり、その場合すべての外部へのリクエストはブロックされます」）。

#### 動作範囲の現実的な想定

| 種別 | 可否 |
| --- | --- |
| dボタン、ページ遷移、地域選択、クイズ選択肢 | ○ 受信機内で完結するため動作 |
| NVRAM への保存・読み出し | ○ web-bml に実装あり |
| 通信系コンテンツの取得（HTTP GET） | △ プロキシ経由なら技術的には可能 |
| 応募・投票などのデータ送信 | × 正規受信機以外からのアクセスは想定外。実装しない |

## 6. 技術選定の記録（採用しなかったもの）

### ブラウザ側での字幕デコード（aribb24.js）— 不採用

B24 をそのままブラウザへ送り、`feedB24(payload, pts, dts)` に食わせる構成。
クライアントで完結しプロセスも増えないが、**録画と live で描画系が二重になる**。
サーバで描けば見た目が完全に一致し、外字も背景の箱も放送どおりに出る。
帯域の増加は実測で毎秒 8.3KB と、映像の隣では無視できる。

サーバ負荷（live 1本につき ffmpeg がもう1プロセス）が問題になる規模なら、
この構成へ戻す余地は残る。**サイドチャネルの形は変わらない**（B24 を 0x20 で流すだけ）。

### H.264 + MPEG-TS + mpegts.js で先に全機能を通す — 不採用

前例が豊富（KonomiTV / web-bml と同一構成）で、段階を踏む案として有力だった。
**字幕の経路が録画側で先に完成した**ため、あとで捨てるコードを書く理由が無くなった。
Safari や AV1 非対応環境のための H.264 fallback は、段階ではなく**コーデックの設定**として残す。

### GStreamer — 不採用

当初は「tsdemux の private pad で B24 を映像と同一クロック上で取得でき、tee が不要になる」ことを理由に有力視した。**データ放送要件の追加によりこの論拠は失効**（psisiarc が独立プロセスで TS を読むため tee は必須）。

残る比較では ffmpeg が優位:

- web-bml 自体が ffmpeg 前提（`FFMPEG` 環境変数、既定形式 `h264-mpegts`）
- tsreadex / psisiarc / tsreplace / KonomiTV も同様の CLI パイプライン形
- QSVEncC / NVEncC / VCEEncC が使える（GStreamer からは不可）
- GStreamer は ARIB/ISDB の知識・前例ゼロ
- 放送波の不安定さ（解像度変化、ステレオ⇄デュアルモノ）は tsreadex が吸収済み
- AV1 over WebRTC は MediaMTX 経由で取得可能
- **libaribcaption を組み込める**（`--enable-libaribcaption`。字幕の描画をそのまま使える）

### ffmpeg の WHIP muxer — 不採用

音声 Opus・映像 H.264 固定かつ experimental。AV1 が使えない。
WebRTC が必要な場合は MediaMTX を経由する。

### MPEG-TS への AV1 多重 — 保留

AOM 公式仕様（AOMediaCodec/av1-mpeg2-ts、stream_type 0x06 + format_identifier `AV01`）は存在するが、
FFmpeg は PR、VLC は MR、GStreamer は WIP 段階。ブラウザ側デマクサも存在しない。継続監視する。

### Media over QUIC — 低遅延化の候補

字幕・データ放送を第一級のトラックとして扱える唯一の選択肢だが、IETF ドラフト段階。

## 7. 既知のリスク・未解決事項

| 項目 | 内容 | 対応 |
| --- | --- | --- |
| AV1 エンコード負荷 | ソフトウェアでのリアルタイム処理は困難 | ハードウェアエンコーダ前提。非対応環境は H.264 に切り替え |
| Safari 非対応 | Opus in mp4 / AV1 が MSE で通らない | H.264 + AAC の設定に切り替え |
| 字幕用の2本目の ffmpeg | live 1本につきプロセスが1つ増える | 実測で負荷を確認。問題なら aribb24.js 構成へ戻す（§6） |
| 字幕の拡大 | 絵なので、拡大すると文字も引き伸ばされる | `-canvas_size` を表示解像度に合わせる |
| 字幕と映像のズレ | 字幕はエンコードを通らないぶん早く届く | 補正値を設定で持つ（§5.4） |
| web-bml の実装範囲 | STD-B24 / TR-B14 / TR-B15 の部分実装。一部イベント・API 未実装 | 実際のチャンネルで動作確認。完全互換は期待しない |
| web-bml の通信機能 | 実装の有無・範囲を未確認 | ソース（`client/`, `documents/`）で要確認 |
| カルーセル初期表示 | 数秒周期の繰り返し送出のため初期表示に数秒かかる | 仕様上の制約。低遅延要件とは別軸として扱う |
| BML のレイアウト | 映像プレーンの座標系前提 | 字幕と共通のオーバーレイ層を作り、リサイズ追従を一元化 |
| 規約面 | 通信系サーバへの非受信機アクセス | 個人の視聴環境の範囲に留める |
