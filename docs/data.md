# どこに何を持つか

mirakc と denpa は同じものを二重に知りうる。どちらが持つかを決めておかないと、
画面と実際が食い違ったときにどちらが正しいか分からなくなる。

**分け方は1つだけ。「電波から今わかること」は mirakc に都度聞き、
「後から要るもの」は denpa が自分のDBに写す。**

## mirakc に都度聞くもの

denpa は写さない。聞けなければ、その部分だけ出さない。

| もの | 口 | 使うところ |
| --- | --- | --- |
| チューナーの空き | `/api/tuners` | 予約の衝突解決、チューナー画面 |
| チャンネル定義 | `/api/channels` | チューナー画面 |
| mirakc のバージョン・生死 | `/api/version` | チューナー画面 |
| 放送そのもの | `/api/services/{id}/stream` | 録画、ロゴ収集 |

**写さない理由は、写した瞬間に嘘になるから。** チューナーの空きは秒で変わるし、
チャンネル定義は「いま mirakc が何を選局できるか」そのものなので、denpa 側の写しを
見せると、スキャン直後に設定を書き戻したのに古い顔ぶれが出る、ということになる。

## denpa が持つもの

`DENPA_DB` の SQLite。ロゴだけは PNG のままファイル (`data/logos/`)。

| もの | どこから | なぜ持つか |
| --- | --- | --- |
| 局 (`services`) | mirakc の `/api/services` | 局が消えても、その局の録画は残る。**行は消さず、直近の取り込みで見かけなかったものは画面に出さない** (`CURRENT_SERVICES`) |
| 番組表 (`programs`) | mirakc の `/api/programs` | 下記 |
| 局ロゴ | **放送波から denpa が自分で拾う** | mirakc は TS からロゴを集めない |
| 予約・録画・ルール・設定 | denpa 自身 | mirakc は何も知らない |

### 番組表を写している理由

mirakc は「いま電波に出ている番組表」しか持たない。放送が終われば消えるし、
mirakc を入れ替えれば無くなる。denpa が要るのはそこではない。

- **予約は番組表より長生きする。** 録画が終わったあとも「何を録ったのか」は残る
- **録画に付ける名前と概要は、録ったときの値で固定したい。** 番組表は放送直前まで
  書き換わるので、後から引き直すと別の名前になることがある
- **ルールの判定と衝突解決は SQL でやる。** 数千件の番組に対して JOIN と索引で
  一気に当てる。毎回 HTTP で全件取ってメモリで回すのとは速さが違う
- **mirakc が落ちていても画面は出る。** 番組表と予約一覧は読めるべきもの

写す向きは一方通行 (mirakc → denpa) で、denpa から番組表を書き戻すことはない。

### 取り直しの間隔

| いつ | 何を |
| --- | --- |
| **mirakc が知らせてきたら** ([下記](#取り直す合図は-mirakc-から来る)) | 局と番組表を全件取り直して upsert |
| 10分ごと (`EPG_SYNC_INTERVAL`) | 同上。知らせが途切れたときの保険 |
| 1分ごと (`SERVICE_SYNC_INTERVAL`) | **局だけ**を取り直す ([下記](#局が揃ったことは知らせてくれない)) |
| 10分ごと | ロゴが**無い/1週間より古い**物理チャンネルを1つ、**丸ごと**開いて拾う (空きチューナーがあるときだけ)。1回6分。地上波は CDT、衛星はデータカルーセル (DSM-CC) から |
| チャンネルスキャンの直後 | 1回だけ取り込む。あとは mirakc からの知らせを待つ (下記) |

番組表は**差分ではなく全件**を取って upsert する。全件でも数万件で、都度なら安い。

### 消えた局の持ち物は片付ける

取り込みで見かけなかった局は、**番組表を消し、まだ始めていない予約を取り消す**。
スキャンをやり直すと局は普通に入れ替わるので、置いたままにしていた頃は、もう選局
できない局の番組が数万件残って検索にも引っかかり続けていた。予約のほうは録りに
行っても掴めないので、始まるのを待って失敗するより先に取り消す (一覧から戻せる)。

**局の行そのものは残す。** 消すと、その局で録った録画や過去の予約が辿れなくなる。
画面に出さない仕組みは別にある (`CURRENT_SERVICES`)。

**1局も取れなかった回では何もしない。** mirakc が起動直後や不調で空を返すことは
あり、それを「全部消えた」と読むと番組表が丸ごと消える。

### 局を増やせるのは mirakc の入れ直しだけ

denpa が `/api/services` と `/api/programs` を何回叩いても、**mirakc がまだ知らない局は増えない**。
どの局が受信できるかを調べているのは mirakc の `scan-services` で、そちらは

- **物理チャンネルを1つずつ**順番に開く (mirakc-core `epg/service_scanner.rs` の
  `for channel in ...` — 並列にはしない)
- 1チャンネルあたり最大30秒 (`jobs.scan-services.timeout`)
- チューナーの優先度は **−1**。denpa の録画 (2) には譲るが、ロゴ集め (−2) には譲らない
  (番組情報が来なければ何も予約できない。ロゴは出なくても番組表は読める)

チューナーが4本あっても**使うのは常に1本**で、34チャンネルあれば10〜17分かかる。
denpa 側から速めたり並べたりする口は無い (mirakc 3.4.79 の API に jobs を叩く道は無い)。

走るのは**起動したとき** (`services.json` が古いとき) と、既定では 8:01 と 20:01。
つまり**急がせる手はひとつだけで、mirakc を入れ直すこと**。チューナー画面の
「mirakc を入れ直す」がそれで、エージェントが mirakc を止めて起こし直す
(「覚えている局を捨てる」を付けると `services.json` ごと捨てる)。
チャンネルスキャンの最後にも同じことをしている。

以前は denpa 側に「局を取り直す」があり、局が増えなくなるまで50秒おきに
`/api/services` を叩き直していた。**待っている相手を急かす力は無く**、
取り込みが遅れているだけのように見せていたので、やめた。
揃うたびに mirakc が `/events` で知らせてくるので、denpa は待ち構えるだけでいい。

### 取り直す合図は mirakc から来る

mirakc は起きたことを **`GET /events`** (SSE) で流している。

> **`/api` の下ではなく root にある。** OpenAPI (`/api/docs`) は `/api` 配下しか
> 載せないので、そこだけ見て「イベント配信は無い」と判断すると取りこぼす
> (一度そう判断して、10分ごとに覗きに行く作りにしていた)。

| イベント | 中身 | denpa の使い道 |
| --- | --- | --- |
| `epg.programs-updated` | `{serviceId}` | 番組表を取り直す |
| `onair.program-changed` | `{serviceId}` | 録画中の終了時刻を読み直す ([下記](#放送の延長に追従する)) |
| `tuner.status-changed` | `{tunerIndex}` | チューナー画面を更新する |
| `recording.*` `timeshift.*` | — | mirakc 自身の録画機能。denpa は使わない |

番組表が更新されると**局の数だけ**知らせが飛んでくる (実機で30件ほど連続) ので、
静まるのを待ってから1回だけ取り直す (`EPG_EVENT_DEBOUNCE`)。

### 局が揃ったことは知らせてくれない

mirakc は局と番組表を**別々に持っている**のに、`/events` に流れてくるのは番組表の
ぶんだけ (`epg.programs-updated`) で、局が揃ったことを知らせるイベントは無い。
取り込みを知らせ任せにしていた頃は、**初回起動やスキャン直後の「局は分かったが
番組表はこれから」の間、denpa の番組表が空のまま**だった。実機で mirakc 側が
125局 / 番組 0 のとき、denpa 側は2局。番組表が埋まるのは数十分先になる。

なので**局だけを1分ごとに覗きに行く** (`SERVICE_SYNC_INTERVAL`)。番組表を取らない
ぶん軽く、局の一覧は数十KBしかない。数が変わったときだけ画面へ知らせる
(毎回知らせると、開いている端末が何も変わっていないのに1分おきに読み直す)。

**定期実行は保険として残してある。** 途切れたら繋ぎ直すようにしてあるが、
黙って止まる可能性まで消せるわけではないので、`EPG_SYNC_INTERVAL` (10分) と
`ONAIR_POLL_INTERVAL` (5分) で必ず追い付くようにしてある。

## mirakc にあって Mirakurun に無いもの

mirakc は Mirakurun 互換だが、同じではない。実際に動かしているものの `/api/docs`
(OpenAPI) を見て、使えるものと使わないものを決めた結果。

| 口 | 使う? | 理由 |
| --- | --- | --- |
| `/api/iptv/playlist` `/api/iptv/xmltv` | **使う** | Kodi のライブTV。denpa は通さず mirakc に直接繋ぐ ([architecture.md](architecture.md#ライブ視聴)) |
| `/api/programs/{id}/stream` | **使う** | **録画はこれで開く。** 番組の切れ目を実際の放送 (EIT[p/f]) で決めてくれる。下記 |
| `/api/programs/{id}` | **使う** | 録画中の終了時刻を読む。上のストリームが立てた追従役が書き換える |
| `/api/onair` `/api/onair/{id}` | 使わない | 同じものを番組IDから引けるので要らない (`/api/programs/{id}` で足りる) |
| `/api/status` | 使わない | いまのところ中身が薄い (チャンネル未設定だと `{}`) |
| `/api/services/{id}/programs` | 使わない | 全件取得で足りる (上記) |
| **`/events`** (`/api` の下ではない) | **使う** | 番組表の取り直しと放送の延長の合図 ([上記](#取り直す合図は-mirakc-から来る)) |
| `/api/services/{id}/logo` | 使わない | mirakc は**放送波からロゴを集めない**。設定でファイルを指定する仕組みだけなので、denpa が自分で拾う |

### 放送の延長に追従する

番組表の時刻は**予定**でしかない。野球が延びれば後ろの番組もずれるので、
時計だけで録ると尻切れになる。

追従の元は **EIT[p/f]** (いま流れている番組と次の番組)。番組表が使う
EIT[schedule] と違い、p/f は実際の放送に合わせて書き換わる。mirakc はこれを
「on-air program tracker」として持っている。

立て方は2通りあり、**チューナーの食い方がまるで違う**。

- **設定で立てる (`onair-program-trackers` の `local`)** … 1分ごとに
  `mirakc-arib collect-eitpf` を回して p/f を拾う。`uses.tuner` に書いた
  **チューナーを1本まるごとこれ専用に取られる**。地上波2本の環境で1本を
  見張りに使うと、同時録画が1本に落ちる。**採らない**
- **録画のついでに立てる** … `/api/programs/{id}/stream` を UA `EPGStation/…` で
  叩くと、mirakc がその**ストリームに相乗りする一時的な追従役**を作る
  (`SpawnTemporalTracker` は `uses.tuner` を空にして `stream_id` を渡すので、
  チューナーは増えない)。録画が終わって1分ほどで消える。**こちらを採った**

denpa はこうしている。

1. 録画は `/api/programs/{id}/stream` で開く (UA は `EPGStation/denpa`)。
   mirakc は番組が始まるまで1バイトも出さず、**番組が終わった2秒後に閉じる**。
   切れ目を決めるのが番組表ではなく放送になるので、頭に前番組が混ざらないし、
   延びれば延びたぶんだけ録れる
2. `onair.program-changed` が来たら `/api/programs/{id}` を読み直し、終わりが
   **後ろへ動いていたら**予約と録画の終了時刻も動かす。動かさないとスケジューラが
   元の時刻で止めてしまう。前へ動いても縮めない (まだ流れているのに切ると
   取り返しがつかない)
3. 番組単位で開いても**何も流れてこないまま 90 秒**経ったら、サービス単位に
   落として録り続ける。EIT[p/f] が来ない局に当たったときの逃げ道。
   mirakc は番組が始まるまで応答ヘッダも返さないことがあるので、
   この見張りは**開く前から**掛けてある


**残っている穴**: 延長したぶん後ろの予約と重なっても、録画中のものは競合計算の
対象外なので自動では調停されない。同じ物理チャンネルなら mirakc がチューナーを
共有するので実害は無いが、別チャンネルでチューナーが埋まっていると後続が録れない。

## 消えないものは置かない

DBに残り続けるものには必ず期限を切る。1台のサーバで何年も動かすものなので、
放っておくと一覧が伸びるだけで探すのが遅くなる。

| もの | いつ消えるか |
| --- | --- |
| 番組表 (`programs`) | 終わってから1日 |
| 終わった予約 | 2週間 (取り消し・録り逃しか、もう録り始めたもの) |
| 削除済みの録画の行 | 同上 |
| エンコードの記録 | 同上。ただし**録画ごとに最新の1件は残す** (一覧の状態表示がそれを見ている) |
| 局 (`services`) | 消さない。代わりに画面から外す (上記) |
| ルール・設定・局ロゴ | 消さない (ユーザーが入れたもの) |

## この分け方で困るところ

- **チャンネルの顔ぶれだけは両方が知っている。** denpa の `services` (前回の EPG 取得
  時点) と mirakc の `channels` (いまの設定) で、スキャン直後は食い違う。これは
  隠さずチューナー画面に**両方並べて**出している。食い違い自体が「スキャンしたのに
  EPG をまだ取り直していない」という情報になる
- **番組表を写しているので、mirakc 側だけを入れ替えると古い番組が残る。** 終わった
  番組は `pruneOldPrograms` が消すので、放っておいても数日で揃う
