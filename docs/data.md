# どこに何を持つか

エージェントと denpa は同じものを二重に知りうる。どちらが持つかを決めておかないと、
画面と実際が食い違ったときにどちらが正しいか分からなくなる。

**分け方は1つだけ。「機材の今」はエージェントに都度聞き、
「電波から読んだもの」と「後から要るもの」は denpa が自分のDBに持つ。**

エージェントは**中身を読まない**。NIT も SDT も EIT も解かず、掴んだチャンネルの
TS をそのまま流すだけ ([roadmap.md](roadmap.md))。読むのは全部こちら側で、
足場は `src/lib/ts/` にある。

## エージェントに都度聞くもの

denpa は写さない。聞けなければ、その部分だけ出さない。

| もの | 口 | 使うところ |
| --- | --- | --- |
| チューナーの空きと、いま誰が掴んでいるか | `/denpa/tuners` | 予約の衝突解決、チューナー画面 |
| 選局できるチャンネル (スキャンの結果) | `/denpa/channels` | 局の取り込み、番組表集め、チューナー画面 |
| スキャンの結果を預ける | `PUT /denpa/channels` | チャンネルスキャン |
| 繋いである機材を書き換える | `PUT /denpa/tuners` | チューナー画面 |
| 放送そのもの | `/denpa/stream?type=…&channel=…` | 録画、番組表集め、ロゴ収集 |
| カードリーダーの状態 | `/denpa/card` | チューナー画面 |

**写さない理由は、写した瞬間に嘘になるから。** チューナーの空きは秒で変わるし、
チャンネル定義は「いま何を選局できるか」そのものなので、denpa 側の写しを見せると、
スキャン直後なのに古い顔ぶれが出る、ということになる。

**掴み方は1つしかない。** 物理チャンネルを丸ごと開くだけで、mirakc にあった
「サービス単位」「番組単位」に当たるものは無い。局を選り分けるのは denpa
(`ts/service-filter.ts`)、番組の切れ目を見るのも denpa (`ts/eit.ts`)。

## denpa が持つもの

`DENPA_DB` の SQLite。ロゴだけは PNG のままファイル (`data/logos/`)。

| もの | どこから | なぜ持つか |
| --- | --- | --- |
| 局 (`services`) | エージェントの `/denpa/channels` (元は SDT) | 局が消えても、その局の録画は残る。**行は消さず、直近の取り込みで見かけなかったものは画面に出さない** (`CURRENT_SERVICES`) |
| 番組表 (`programs`) | **放送波の EIT を denpa が自分で読む** | 下記 |
| 局ロゴ | **放送波の CDT / データカルーセルを denpa が自分で読む** | 下記 |
| 予約・録画・ルール・設定 | denpa 自身 | エージェントは何も知らない |

局の内部ID (`services.id`) は `networkId * 100000 + serviceId`。**mirakc と同じ
作り方**にしてあるので、過去の録画も予約もそのまま辿れる。番組のIDも同じで、
`局の内部ID * 100000 + event_id`。

### 番組表を写している理由

電波に出ているのは「いま流れている番組表」だけで、放送が終われば消える。
denpa が要るのはそこではない。

- **予約は番組表より長生きする。** 録画が終わったあとも「何を録ったのか」は残る
- **録画に付ける名前と概要は、録ったときの値で固定したい。** 番組表は放送直前まで
  書き換わるので、後から引き直すと別の名前になることがある
- **ルールの判定と衝突解決は SQL でやる。** 数千件の番組に対して JOIN と索引で
  一気に当てる
- **チューナーが塞がっていても画面は出る。** 番組表と予約一覧は読めるべきもの

### 番組表の集め方

**mirakc から引き取っていちばん変わったところ。**

| | mirakc | denpa |
| --- | --- | --- |
| 並列 | **常に1本** (チューナーが4本あっても) | **空いているだけ**並べる |
| 周期 | 1日2回 (8:21 / 20:21) | 30分ごとに「集め直すべき局」を選び直す |
| 順番 | 設定に並んでいる順 | **番組表が薄い局から** |
| 打ち切り | 30秒 新しい EIT が来なければ | **EIT 自身が「どこまであるか」を言っている**ので、揃った時点で離す |
| 録画中 | 取り合いになる | 同じチャンネルなら**相乗り** (チューナーは増えない) |

実測で mirakc は52チャンネルの1周に1時間以上かかり、それが1日2回だった。

集め終わりの判定は `ts/eit.ts` の `ScheduleProgress`。EIT のセクションは8本ずつの
セグメントに分かれていて、`segment_last_section_number` が「このセグメントで
実際に使っている最後の番号」を言う。**使っていない番号は永久に来ない**ので、
そこまで揃えばそのセグメントは終わり。これを見ずに「0〜last_section_number が
全部」で待つと、いつまでも終わらない。

**同じことが `table_id` にもある。** 1つの `table_id` が受け持つのは4日ぶんで、
基本は `0x50` から、詳細は `0x58` から始まる。8日ぶんの放送なら実際に流れてくるのは
`0x50` `0x51` と `0x58` `0x59` だけで、**`0x52`〜`0x57` は永久に来ない**。
`0x50` から `last_table_id` まで全部を待っていた頃は、**詳細を積んでいる局が一度も
「揃った」にならなかった**。

**版 (`version_number`) も `table_id` ごとに別々**に振られる。局に1つだけ持っていた
頃は、基本と詳細を行き来するたびに数えたものを全部捨てていた。

この2つが重なって、実機ではどのチャンネルも上限まで開きっぱなしのうえ、
**先の日ほど題名が埋まらなかった** (TBS1 は当日 20/21 に対し3〜5日後が 0)。
先の日ぶんのセクションは流れてくる間隔が長いので、上限の中に一度も回ってこない。

| いつ | 何を |
| --- | --- |
| 起動直後に1回 | 番組表を集める。薄い局から行くので、数分で画面に出る |
| 30分ごと (`EPG_COLLECT_INTERVAL`) | 集め直すべき局を選び直す |
| 1分ごと (`CHANNEL_SYNC_INTERVAL`) | **局だけ**を取り直す (スキャンの結果はここで届く) |
| **録画している間ずっと** | そのチャンネルの EIT は只で読める。5分ごとに書き出す |
| 誰かがチューナーを開いたら | その選局に**相乗り**して局ロゴを拾う。ロゴが**無い/1週間より古い**局だけが対象 |
| 30分ごと | CM検出用のロゴ (`.lgd`) をまだ覚えていない局を1つ。**開いているチャンネルなら只**で、そこから先に回る |
| スキャンが終わったら | 局を取り込み直して、番組表を集め直す |
| 「番組表をいますぐ集める」を押したら | **全チャンネルを、録画以外を蹴る強さで** (下記) |

「集め直すべき局」は2つの条件のどちらか。**番組表が3日先まで埋まっていない**
(`EPG_MIN_COVERAGE`) か、**6時間 行っていない** (`EPG_CHANNEL_INTERVAL`)。
前者は再起動しても分かる指標なので、Pod が入れ替わっても全チャンネルを
回し直すことにはならない。

**ただし、行った直後は行き直さない** (`EPG_CHANNEL_RETRY`、既定2時間)。番組表が
**永久に埋まらない局**のための下限で、実機には受信できない CS が24局残っていて、
開いても EIT が1件も来ない。「薄いから行く」だけで選んでいた頃は、そこが30分ごとの
周回で毎回選ばれ、1本ぶんの上限 (`EPG_CHANNEL_TIMEOUT`) まで開きっぱなしになっていた。
**掴めなかった回は数えない** — 録画に譲って開けなかっただけの局まで休ませると、
そのぶん番組表が古くなる。

**番組表に出てこない局は「薄い」と数えない。** エージェントは TS に居る全部の局を
返すが、denpa は映像の入っていない局を落とす (データ放送・ワンセグ)。これを
「0まで埋まっている = いちばん薄い」と読んでいた頃は、地上波がほぼ全局これを
積んでいるので**地上波が丸ごと毎周回の対象**になっていた。

**同じ TS を指す枠は1回だけ開く。** 衛星は `BS01_0` のような相対番号で選ぶが、
無い番号を指すと復調器は先頭の TS を返す。スキャンでも落としているものの、
**控えを書いたのが古いスキャンだと写しが残る** — 実機の `channels.json` がまさに
それで、BS 35 枠のうち 9 枠が写しのまま、衛星の1周が 26 ではなく 35 回になっていた。
開く側でも落とすので、控えが何であれ二度は開かない。

**「最後に集めた時刻」は局から引く。** `services.channel` に入るのは「最後に
取り込んだときの枠の名前」1つだけなので、同じ TS を指す枠が2つあると片方が必ず
「一度も集めていない」ことになる。上の9枠は永久にまっさらに見えて、周回のたびに
開かれていた。

**開くのはチューナー1本につき1人**で、種別をまたいで1つの列を引く。
種別ごとに「その種別のチューナー本数」だけ並べていた頃は、BS と CS を
同時に集めると**衛星の本数を二重に数えていた** (同じ2本が BS でも CS でも
1人前に見える)。溢れたぶんは 409 で弾かれ、その回は集められないまま落ちる。

### 入れたばかりのとき — 「番組表をいますぐ集める」

普段の番組表集めは**いちばん弱い部類** (`EPG` = 3) で開く。録画にもスキャンにも
譲るのが正しいが、**入れた直後は番組表が空**で、そこでスキャンやロゴ集めが
動いていると、いつまでも画面に何も出ない。

チューナー画面のこのボタンを押している間だけ、**優先度 8** で掴む。録画 (10) は
蹴らないが、スキャン (5) もロゴ (1) も蹴る。選り好みもしない — 上の2条件を
無視して**全チャンネル**を、薄いほうから回る (さっき集め終えた直後に押しても
1本も回らない、では押した意味が無い)。

**走っている周回があれば、その回を強くする。** 開くのは1チャンネルずつなので、
次に開くところから効く。待たせて仕切り直すより早い。

### 録画中の番組表はただで手に入る

録画は物理チャンネルを丸ごと開いているので、そのチャンネルの EIT も
一緒に流れてくる。**読んで捨てる理由が無い**ので、5分ごとに書き出している。
番組表集めがそのチャンネルへ行く手間がまるごと省ける。

放送の延長への追従も同じところから来る ([下記](#放送の延長に追従する))。

### 消えた局の持ち物は片付ける

取り込みで見かけなかった局は、**番組表を消し、まだ始めていない予約を取り消す**。
スキャンをやり直すと局は普通に入れ替わるので、置いたままにしていた頃は、もう選局
できない局の番組が数万件残って検索にも引っかかり続けていた。予約のほうは録りに
行っても掴めないので、始まるのを待って失敗するより先に取り消す (一覧から戻せる)。

**局の行そのものは残す。** 消すと、その局で録った録画や過去の予約が辿れなくなる。
画面に出さない仕組みは別にある (`CURRENT_SERVICES`)。

**1回見かけなかっただけでは片付けない** (`SERVICE_FORGET_AFTER`、既定30分)。一覧は
1分ごとに取り直しているので、ここまで続けて見かけないなら本当に居ない。1回で決めて
いた頃は、エージェントから欠けた一覧が返った拍子に**現役の局の予約が44件まとめて
取り消された**。

**1局も取れなかった回では何もしない。** エージェントが起動直後や不調で空を返すことは
あり、それを「全部消えた」と読むと番組表が丸ごと消える。

### 局を増やすのはチャンネルスキャンだけ

どの局が受信できるかの控えを持っているのはエージェントで、その中身は
**チャンネルスキャンの結果** (`channels.json`) そのもの。番組表を何回集め直しても
局は増えない。増やしたいときはスキャンをやり直す。

**中身を作るのは denpa。** 総当たりの選局はエージェントに頼むが、NIT も SDT も
解かないので「何が居たか」は分からない。読むのはこちらで、見つけた顔ぶれを
`PUT /denpa/channels` で預ける。控えをあちらに置くのは、アンテナに何が映るかが
機材ごとの話だから (エージェントを増やせば顔ぶれも変わる)。

mirakc の頃は、局を調べるのも向こうの仕事 (`epg.scan-services`) だったので、
「局が足りない」ときに効くのは **mirakc を入れ直すこと**だけだった。
起動時に取りに行く性質を利用していたわけで、チューナー画面に「mirakc を入れ直す」
というボタンがあったのはそのため。**いまは何も再起動しない。**

### 時刻合わせ (TDT / TOT) は持たない

mirakc には `epg.sync-clocks` があって、放送波の時刻と自分の時計を突き合わせていた。
denpa は**やらない** — 録画の開始と終了は壁の時計で決めていて、放送波の時刻を
基準にしているところが1つも無いため。ホストの時刻が合っていることのほうが大事で、
そちらは NTP の仕事。

### 知らせはエージェントから来る

エージェントは起きたことを **`GET /denpa/events`** (SSE) で流している。

| イベント | denpa の使い道 |
| --- | --- |
| `tuners` | チューナー画面を更新する。開いた選局に**相乗り**してロゴを拾う |
| `channels` | 局が入れ替わった。取り込み直して番組表も集め直す |

スキャンの進み具合はここには乗らない。**回しているのは denpa 自身**なので、
自分の画面へ直接流す。

**定期実行は保険として残してある。** 途切れたら繋ぎ直すようにしてあるが、
黙って止まる可能性まで消せるわけではない。

### 放送の延長に追従する

番組表の時刻は**予定**でしかない。野球が延びれば後ろの番組もずれるので、
時計だけで録ると尻切れになる。

追従の元は **EIT[p/f]** (いま流れている番組と次の番組)。番組表が使う
EIT[schedule] と違い、p/f は実際の放送に合わせて書き換わる。

**問い合わせる相手が要らない。** 録画しているチャンネルの TS にそのまま
流れてくるので、読むだけで分かる。mirakc の頃は「番組単位のストリームで開いて
向こうに追従役を立てさせ、`/api/programs/{id}` を読み直す」という段取りが要り、
その仕掛けを試すためだけのテストまであった。

いまの動き:

1. 録画は物理チャンネルを丸ごと開き、`ServiceFilter` でその局だけを書き出す
2. 同じ TS から EIT[p/f] を読む。`running_status` が「放送中」の番組が
   録画中のもの (event_id 一致) なら、その終了時刻を見る
3. **後ろへ動いていたら**予約と録画の終了時刻も動かす。動かさないとスケジューラが
   元の時刻で止めてしまう。**前へ動いても縮めない** (まだ流れているのに切ると
   取り返しがつかない)

EIT[p/f] を流さない局に当たっても、番組表の時刻どおりには録れる。追従できないだけ。

**残っている穴**: 延長したぶん後ろの予約と重なっても、録画中のものは競合計算の
対象外なので自動では調停されない。同じ物理チャンネルならエージェントが相乗り
させるので実害は無いが、別チャンネルでチューナーが埋まっていると後続が録れない。

## 消えないものは置かない

DBに残り続けるものには必ず期限を切る。1台のサーバで何年も動かすものなので、
放っておくと一覧が伸びるだけで探すのが遅くなる。

| もの | いつ消えるか |
| --- | --- |
| 番組表 (`programs`) | 終わってから1日 |
| 終わった予約 | 2週間 (取り消し・録り逃しか、もう録り始めたもの) |
| 削除済みの録画の行 | 同上 |
| エンコードの記録 | 同上。ただし**録画ごとに最新の1件は残す** (一覧の状態表示がそれを見ている) |
| 局 (`services`) | 消さない。代わりに画面から外す (上記) |
| ルール・設定・局ロゴ | 消さない (ユーザーが入れたもの) |

## この分け方で困るところ

- **チャンネルの顔ぶれだけは両方が知っている。** denpa の `services` (前回の取り込み
  時点) とエージェントの `channels` (いまのスキャン結果) で、スキャン直後は食い違う。
  これは隠さずチューナー画面に**両方並べて**出している。食い違い自体が
  「スキャンしたのに、まだ取り込んでいない」という情報になる
- **番組表を持っているので、集め直すまでは古い番組が残る。** 終わった番組は
  `pruneOldPrograms` が消すので、放っておいても数日で揃う
