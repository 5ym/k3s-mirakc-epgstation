# どこに何を持つか

エージェントと denpa は同じものを二重に知りうる。どちらが持つかを決めておかないと、
画面と実際が食い違ったときにどちらが正しいか分からなくなる。

**分け方は1つだけ。「機材の今」はエージェントに都度聞き、
「電波から読んだもの」と「後から要るもの」は denpa が自分のDBに持つ。**

エージェントは**中身を読まない**。NIT も SDT も EIT も解かず、掴んだチャンネルの
TS をそのまま流すだけ ([agent.md](agent.md))。読むのは全部こちら側で、
足場は `src/lib/ts/` にある。

## エージェントに都度聞くもの

denpa は写さない。聞けなければ、その部分だけ出さない。

| もの | 口 | 使うところ |
| --- | --- | --- |
| チューナーの空きと、いま誰が掴んでいるか | `/denpa/tuners` | 予約の衝突解決、チューナー画面 |
| 選局できるチャンネル (スキャンの結果) | `/denpa/channels` | 局の取り込み、番組表集め、チューナー画面 |
| スキャンの結果を預ける | `PUT /denpa/channels` | チャンネルスキャン |
| 繋いである機材を書き換える | `PUT /denpa/tuners` | チューナー画面 |
| 放送そのもの | `/denpa/stream?type=…&channel=…` | 録画、番組表集め、ロゴ収集 |
| カードリーダーの状態 | `/denpa/card` | チューナー画面 |

**写さない理由は、写した瞬間に嘘になるから。** チューナーの空きは秒で変わるし、
チャンネル定義は「いま何を選局できるか」そのものなので、denpa 側の写しを見せると、
スキャン直後なのに古い顔ぶれが出る、ということになる。

**掴み方は1つしかない。** 物理チャンネルを丸ごと開くだけで、「サービス単位」
「番組単位」のような開き方は無い。局を選り分けるのは denpa
(`ts/service-filter.ts`)、番組の切れ目を見るのも denpa (`ts/eit.ts`)。

## denpa が持つもの

`DENPA_DB` の SQLite。ロゴだけは PNG のままファイル (`data/logos/`)。

| もの | どこから | なぜ持つか |
| --- | --- | --- |
| 局 (`services`) | エージェントの `/denpa/channels` (元は SDT) | 局が消えても、その局の録画は残る。**行は消さず、直近の取り込みで見かけなかったものは画面に出さない** (`CURRENT_SERVICES`) |
| 番組表 (`programs`) | **放送波の EIT を denpa が自分で読む** | 下記 |
| 局ロゴ | **放送波の CDT / データカルーセルを denpa が自分で読む** | 下記 |
| 予約・録画・ルール・設定 | denpa 自身 | エージェントは何も知らない |

局の内部ID (`services.id`) は `networkId * 100000 + serviceId`。番組のIDも同じで、
`局の内部ID * 100000 + event_id`。**この作り方は変えられない** — 録画も予約も
これを参照しているので、変えると過去の録画が辿れなくなる。

### 番組表を写している理由

電波に出ているのは「いま流れている番組表」だけで、放送が終われば消える。
denpa が要るのはそこではない。

- **予約は番組表より長生きする。** 録画が終わったあとも「何を録ったのか」は残る
- **録画に付ける名前と概要は、録ったときの値で固定したい。** 番組表は放送直前まで
  書き換わるので、後から引き直すと別の名前になることがある
- **ルールの判定と衝突解決は SQL でやる。** 数千件の番組に対して JOIN と索引で
  一気に当てる
- **チューナーが塞がっていても画面は出る。** 番組表と予約一覧は読めるべきもの

### 番組表の集め方

**番組表を持っているのが denpa なので、集め方もこちらで決められる。**

| | |
| --- | --- |
| 並列 | チューナーが**空いているだけ**並べる |
| 周期 | 30分ごとに「集め直すべき局」を選び直す |
| 順番 | **番組表が薄い局から** |
| 打ち切り | **EIT 自身が「どこまであるか」を言っている**ので、揃った時点で離す |
| 録画中 | 同じチャンネルなら**相乗り** (チューナーは増えない) |

集め終わりの判定は `ts/eit.ts` の `ScheduleProgress`。EIT のセクションは8本ずつの
セグメントに分かれていて、`segment_last_section_number` が「このセグメントで
実際に使っている最後の番号」を言う。**使っていない番号は永久に来ない**ので、
そこまで揃えばそのセグメントは終わり。これを見ずに「0〜last_section_number が
全部」で待つと、いつまでも終わらない。

**同じことが `table_id` にもある。** 1つの `table_id` が受け持つのは4日ぶんで、
基本は `0x50` から、詳細は `0x58` から始まる。8日ぶんの放送なら実際に流れてくるのは
`0x50` `0x51` と `0x58` `0x59` だけで、**`0x52`〜`0x57` は永久に来ない**。
`0x50` から `last_table_id` まで全部を待っていた頃は、**詳細を積んでいる局が一度も
「揃った」にならなかった**。

**版 (`version_number`) も `table_id` ごとに別々**に振られる。局に1つだけ持っていた
頃は、基本と詳細を行き来するたびに数えたものを全部捨てていた。

この2つが重なって、実機ではどのチャンネルも上限まで開きっぱなしのうえ、
**先の日ほど題名が埋まらなかった** (TBS1 は当日 20/21 に対し3〜5日後が 0)。
先の日ぶんのセクションは流れてくる間隔が長いので、上限の中に一度も回ってこない。

**先行実装と突き合わせた。** Mirakurun は版を `version[table_id]` で持っていて
(`EPG.ts` の `isOutOfDate`)、**局に1つではない**。基本と詳細を別々に持って、
読むときに重ねるのも同じ。

**「揃った」で閉じるのは denpa だけがやっていること。** よそは時間で打ち切る
作りなので、こちらの早じまいは*余分な最適化*にあたる。だからこそ判定が
間違っていると、上のように黙って取りこぼす。

| いつ | 何を |
| --- | --- |
| 起動直後に1回 | 番組表を集める。薄い局から行くので、数分で画面に出る |
| 30分ごと (`EPG_COLLECT_INTERVAL`) | 集め直すべき局を選び直す |
| 1分ごと (`CHANNEL_SYNC_INTERVAL`) | **局だけ**を取り直す (スキャンの結果はここで届く) |
| **録画している間ずっと** | そのチャンネルの EIT は只で読める。5分ごとに書き出す |
| 誰かがチューナーを開いたら | その選局に**相乗り**して局ロゴを拾う。ロゴが**無い/1週間より古い**局だけが対象 |
| 30分ごと | CM検出用のロゴ (`.lgd`) をまだ覚えていない局を1つ。**開いているチャンネルなら只**で、そこから先に回る |
| スキャンが終わったら | 局を取り込み直して、番組表を集め直す |
| 「番組表をいますぐ集める」を押したら | **全チャンネルを、録画以外を蹴る強さで** (下記) |

「集め直すべき局」は2つの条件のどちらか。**番組表が3日先まで埋まっていない**
(`EPG_MIN_COVERAGE`) か、**6時間 行っていない** (`EPG_CHANNEL_INTERVAL`)。
前者は再起動しても分かる指標なので、Pod が入れ替わっても全チャンネルを
回し直すことにはならない。

**ただし、行った直後は行き直さない** (`EPG_CHANNEL_RETRY`、既定2時間)。番組表が
**永久に埋まらない局**のための下限で、実機の CS には、開いても EIT が1件も来ない
チャンネルが4つ (22局) ある。「薄いから行く」だけで選んでいた頃は、そこが30分ごとの
周回で毎回選ばれ、1本ぶんの上限 (`EPG_CHANNEL_TIMEOUT`) まで開きっぱなしになっていた。
**掴めなかった回は数えない** — 録画に譲って開けなかっただけの局まで休ませると、
そのぶん番組表が古くなる。

**番組表に出てこない局は「薄い」と数えない。** エージェントは TS に居る全部の局を
返すが、denpa は映像の入っていない局を落とす (データ放送・ワンセグ)。これを
「0まで埋まっている = いちばん薄い」と読んでいた頃は、地上波がほぼ全局これを
積んでいるので**地上波が丸ごと毎周回の対象**になっていた。

**同じ TS を指す枠は1回だけ開く。** 衛星は `BS01_0` のような相対番号で選ぶが、
無い番号を指すと復調器は先頭の TS を返す。スキャンでも落としているものの、
**控えを書いたのが古いスキャンだと写しが残る** — 実機の `channels.json` がまさに
それで、BS 35 枠のうち 9 枠が写しのまま、衛星の1周が 26 ではなく 35 回になっていた。
開く側でも落とすので、控えが何であれ二度は開かない。

**「最後に集めた時刻」は局から引く。** `services.channel` に入るのは「最後に
取り込んだときの枠の名前」1つだけなので、同じ TS を指す枠が2つあると片方が必ず
「一度も集めていない」ことになる。上の9枠は永久にまっさらに見えて、周回のたびに
開かれていた。

**開くのはチューナー1本につき1人**で、種別をまたいで1つの列を引く。
種別ごとに「その種別のチューナー本数」だけ並べていた頃は、BS と CS を
同時に集めると**衛星の本数を二重に数えていた** (同じ2本が BS でも CS でも
1人前に見える)。溢れたぶんは 409 で弾かれ、その回は集められないまま落ちる。

### 衛星の番組表 — 1中継でも取れる。**それでも TS ごとに開きます**

**BS は、どの中継にも「他の中継ぶんの番組表」が流れています。** 1本開けば
BS 全体の番組表が取れる、ということです。**取りませんでした** — 理由は下記。

EIT は table_id で自TSと他TSに分かれています。denpa がいま読んでいるのは
自TS ぶん (`0x4E` と `0x50-0x5F`) だけで、他TS ぶん (`0x4F` / `0x60-0x6F`) は
捨てています (`ts/eit.ts`)。捨てているものに何が入っているのかを数えました。

#### 実測 (実機 / BS03_0 と BS05_1 に相乗り / 2分 / 372 MB)

| 何 | セクション | 番組 | TSID | 局 | いちばん先 |
| --- | --- | --- | --- | --- | --- |
| `0x4E` いま/次 (自TS) | 199 | 199 | 2 | 4 | 1 日先 |
| `0x4F` いま/次 (他TS) | 1089 | 1041 | **26** | **48** | 1 日先 |
| `0x50-57` 番組表 基本 (自TS) | 230 | 711 | 2 | 3 | 7 日先 |
| `0x58-5F` 番組表 詳細 (自TS) | 70 | 170 | 2 | 2 | 7 日先 |
| `0x60-67` 番組表 基本 (他TS) | 5427 | **18311** | **26** | **43** | **7 日先** |
| `0x68-6F` 番組表 詳細 (他TS) | 111 | 200 | 3 | 3 | 7 日先 |

**2分で、26 の TS・43 局ぶんの番組表が7日先まで来ています。** いま denpa は
これを 11 物理チャンネル × 4 スロットぶん選局し直して集めています。

**ただし詳細 (`0x68-6F`) はほとんど来ません。** 5427 対 111 で、他TS ぶんに
付いてくるのは**番組名と概要まで**。`extended_event_descriptor` (出演者など) は
自分の TS ぶんしか流れていない、と読むのが妥当です。自動予約ルールの
「詳細まで広げる」は、BS ではそこが当たらなくなります。

**CS は別のネットワークなので、これとは別に測る必要があります** (上の TSID は
すべて BS のもの)。

#### やらない — **詳細を全局ぶん取るほうを選びました**

1中継で済ませると、**出演者などの詳細が自分の TS ぶんしか手に入りません**
(上の 5427 対 111)。衛星も全局ぶん詳細が欲しいので、**今までどおり
TS ごとに開きます**。空くチューナーより、番組表の中身のほうを取ります。

`0x60-0x6F` は捨てたままにします。基本だけ先に入れておく手もありますが、
**あとから詳細で上書きする**ことになり、その間だけ詳細の無い番組が
画面に出ます (番組名は同じなので、直ったことにも気付けません)。

代わりに、**同じ TS を二度開かない**ようにしました。下記。

#### 相対番号の穴 — 同じ TS を指す枠が9つあった

衛星は `BS01_0` のような**相対番号**で選びますが、実際に何本乗っているかは
中継ごとに違います。**無い番号を指すと、復調器は先頭の TS を返します**
(断ってはくれません)。

実機のスキャン結果 35 枠のうち、**9 枠が既に知っている TS の写し**でした。

| 枠 | 実体 |
| --- | --- |
| `BS01_3` | `BS01_0` (16400) |
| `BS03_3` | `BS03_0` (16432) |
| `BS05_2` `BS05_3` | `BS05_0` (17488) |
| `BS09_2` `BS09_3` | `BS09_0` (16528) |
| `BS13_3` | `BS13_0` (16592) |
| `BS21_3` | `BS21_0` (18256) |
| `BS23_3` | `BS23_0` (18288) |

**取りこぼしではありません。** 残った 26 TS は、上の EIT 他TS 調査で放送自身が
名乗っていた 26 TS と**完全に一致**します。BS は1本も落ちていません。

放っておくと番組表集めが同じ TS を二度三度と開くので、スキャンの時点で
落とすようにしました (`twinOf`)。衛星の1周が **35 → 26 回**になります。

**開く側でも落とします。** スキャンで落としても、**控えを書いたのが古いスキャンなら
写しが残ります**。実機の `channels.json` がまさにそれで、この対策を入れたあとも
BS 35 枠のまま回り続けていました。しかも `services.channel` に入るのは
「最後に取り込んだときの枠の名前」1つだけなので、**残った9枠は永久に
「一度も集めていない」ことになり**、周回のたびに開かれていました。
番組表集めのほうでも `withoutTwins` で落とし、「最後に集めた時刻」は
枠ではなく**局から**引きます。

### 入れたばかりのとき — 「番組表をいますぐ集める」

普段の番組表集めは**いちばん弱い部類** (`EPG` = 3) で開く。録画にもスキャンにも
譲るのが正しいが、**入れた直後は番組表が空**で、そこでスキャンやロゴ集めが
動いていると、いつまでも画面に何も出ない。

チューナー画面のこのボタンを押している間だけ、**優先度 8** で掴む。録画 (10) は
蹴らないが、スキャン (5) もロゴ (1) も蹴る。選り好みもしない — 上の2条件を
無視して**全チャンネル**を、薄いほうから回る (さっき集め終えた直後に押しても
1本も回らない、では押した意味が無い)。

**走っている周回があれば、その回を強くする。** 開くのは1チャンネルずつなので、
次に開くところから効く。待たせて仕切り直すより早い。

### 録画中の番組表はただで手に入る

録画は物理チャンネルを丸ごと開いているので、そのチャンネルの EIT も
一緒に流れてくる。**読んで捨てる理由が無い**ので、5分ごとに書き出している。
番組表集めがそのチャンネルへ行く手間がまるごと省ける。

放送の延長への追従も同じところから来る ([下記](#放送の延長に追従する))。

### 消えた局の持ち物は片付ける

取り込みで見かけなかった局は、**番組表を消し、まだ始めていない予約を取り消す**。
スキャンをやり直すと局は普通に入れ替わるので、置いたままにしていた頃は、もう選局
できない局の番組が数万件残って検索にも引っかかり続けていた。予約のほうは録りに
行っても掴めないので、始まるのを待って失敗するより先に取り消す (一覧から戻せる)。

**局の行そのものは残す。** 消すと、その局で録った録画や過去の予約が辿れなくなる。
画面に出さない仕組みは別にある (`CURRENT_SERVICES`)。

**1回見かけなかっただけでは片付けない** (`SERVICE_FORGET_AFTER`、既定30分)。一覧は
1分ごとに取り直しているので、ここまで続けて見かけないなら本当に居ない。1回で決めて
いた頃は、エージェントから欠けた一覧が返った拍子に**現役の局の予約が44件まとめて
取り消された**。

**1局も取れなかった回では何もしない。** エージェントが起動直後や不調で空を返すことは
あり、それを「全部消えた」と読むと番組表が丸ごと消える。

### 局を増やすのはチャンネルスキャンだけ

どの局が受信できるかの控えを持っているのはエージェントで、その中身は
**チャンネルスキャンの結果** (`channels.json`) そのもの。番組表を何回集め直しても
局は増えない。増やしたいときはスキャンをやり直す。

**中身を作るのは denpa。** 総当たりの選局はエージェントに頼むが、NIT も SDT も
解かないので「何が居たか」は分からない。読むのはこちらで、見つけた顔ぶれを
`PUT /denpa/channels` で預ける。控えをあちらに置くのは、アンテナに何が映るかが
機材ごとの話だから (エージェントを増やせば顔ぶれも変わる)。

**局が足りないときは、スキャンし直すだけ。** 何も再起動しません。

### チャンネルスキャン

**画面の「チューナー」から実行します。** Mirakurun の走査に合わせてあります。

- 地上波 13〜62ch を総当たり、BS は 01〜23 の各4スロット、CS は 02〜24ch
- 1チャンネル最大30秒。**NIT と SDT が両方揃って**初めて受信できたとみなします
  (SDT だけではどのネットワークのものか分からず、設定に書けません)
- **途中で中断できます。** 十数分かかるので、始めてから「いま録りたい」に気づいた
  ときに待つしかないのは困ります。中断したときは設定を書き換えません
  (途中までの結果で上書きすると、まだ回っていない局の定義が消えます)
- 録るに値するサービス種別だけ残します
- **回すのは denpa** です。1チャンネルずつエージェントに選局を頼み、
  流れてきた TS から NIT と SDT を読みます。エージェントに読ませると、
  ARIB の文字符号から局の選り分けまで**同じものを2箇所に持つ**ことになります
- チューナーの台数ぶん並べて回します。**録画中でも実行できます** — 選局は
  エージェントの取り合いに乗るので、録画が掴んでいるチューナーは使われない
  だけです (空きが無ければ待ち、飛ばしません。飛ばすとそのチャンネルだけ
  設定から消えます)

うまくいかないときのために、失敗の理由は分けて出します。「そもそも何も来なかった」
(配線・デバイス指定を疑う) と「電波は来たのに NIT や SDT が揃わなかった」
(受信環境を疑う) では、次に見るところがまるで違うためです。recisdb が stderr に
書いたもの(「デバイスが使用中」など)も1行だけ添えます。**電波が来たのに揃わなかった
チャンネルだけ、もう一度回します** — NIT は10秒に1回しか流れてこないので、選局が
落ち着くのが遅れると待ち時間の中に1回も入らないことがあるためです。

1チャンネル読み終えたら**接続ごと切ります**。エージェントはそれを合図に選局を畳みます
([agent.md](agent.md#選局は読み手が切るまで終わらない))。畳みそこねると、以降のチャンネルが全部
「受信できませんでした」になります。

局名も SDT から読みます。ARIB の文字符号は独自ですが、番組表を自分で集めるなら
どのみち要るので `ts/aribtext.ts` に寄せてあります。

**探した種別だけ**を差し替えます。地上波だけスキャンしたときに全部を置き換えると
BS と CS が設定から消えます (実際に消して、BS の予約が録れなくなりました)。
**1件も見つからなければ失敗**として扱い、今まで録れていた局を消しません。

見つけた顔ぶれは **`PUT /denpa/channels`** でエージェントに預けます。読んだのは
denpa ですが、控えを持つのはエージェント側にします — アンテナに何が映るかは
機材ごとの話で、エージェントを増やせば顔ぶれも変わるからです。

預かったエージェントは**何も再起動しません**。局が入れ替わったことを
`channels` として知らせるだけで、掴んでいる録画も切れません。
取り込み直して番組表を集め直すのは denpa の側です。

### 時刻合わせ (TDT / TOT) は持たない

放送波には時刻 (TDT / TOT) が流れていて、それと自分の時計を突き合わせる作りの
ものもある。denpa は**やらない** — 録画の開始と終了は壁の時計で決めていて、
放送波の時刻を基準にしているところが1つも無いため。ホストの時刻が合っている
ことのほうが大事で、そちらは NTP の仕事。

### 知らせはエージェントから来る

エージェントは起きたことを **`GET /denpa/events`** (SSE) で流している。

| イベント | denpa の使い道 |
| --- | --- |
| `tuners` | チューナー画面を更新する。開いた選局に**相乗り**してロゴを拾う |
| `channels` | 局が入れ替わった。取り込み直して番組表も集め直す |

スキャンの進み具合はここには乗らない。**回しているのは denpa 自身**なので、
自分の画面へ直接流す。

**定期実行は保険として残してある。** 途切れたら繋ぎ直すようにしてあるが、
黙って止まる可能性まで消せるわけではない。

### 自動予約は「番組表に当て直す」

ルールから予約を作るところは、**足すだけでなく外れたものを消します。** 足すだけだった頃は、
番組表が書き換わって条件から外れた予約がそのまま残り、消す手立てが画面の「取り消し」しか
ありませんでした。番組表を取り込み直したところで毎回当て直します。

**消すのであって「取り消し」にはしません。** 取り消しは*人が押したこと*の記録で、
ルールはそれを二度と作り直しません。番組表が動いただけのものを取り消しにすると、
条件に戻ってきても永久に予約が立たなくなります。ルールを消したときに取り消しの記録を
残していた頃は、**消えたはずのルールの予約が「ルール: (削除済み)」として一覧に並んで**
いました (実機で149件)。

**手違いで消すほうが、余分に録るより高くつきます。** 引っ込めないものが4つあります。

- **手動の予約と、録り始めたもの**
- **番組表からその番組ごと消えているとき。** 「条件から外れた」のか「まだ読めていない」
  のか区別が付きません。**題名が空の番組も同じ**で、放送が名前を出していないのではなく
  こちらがまだ読めていないだけのことがあります (実機で 23,000 件のうち 11,000 件)
- **もうすぐ始まるもの** (`RULE_RETRACT_GRACE`、既定1時間)。番組表は放送直前まで
  書き換わる ([新] が付く、サブタイトルが入る、誤字が直る) ので、その拍子に条件から
  外れても録っておきます
- ただし**ルールごと消された/止められたぶんは、直前でも引っ込めます** — そちらは
  人が押した結果なので迷う理由がありません

**ルールを足したときだけは、そのルールしか見ません。** 新しいルールは他の予約を
外せないので、全ルール × 全番組 (実機で 318 × 25,608) を回し直す理由がありません。

#### 同じ放送は1本だけ — 枝番の局に気をつける

**局は分割放送のために枝番を持っています。** TOKYO MX なら 23608 と 23609 で、
SDT が返す名前は**どちらも「TOKYO MX1」**。分割していない間は**同じ回が両方に
載り**、ルールは素直に両方へ当たります。

実機ではこれで同じ回が2本録れ、さらに**2つのエンコードが同じ名前のファイルへ
同時に書いて中身が壊れました** (片方は `ENOENT` で失敗、残ったほうは復号すると
145行のエラー。焼き直したものは0行)。

そこで、**同じ物理チャンネル・同じ時刻・同じ題名**なら同じ放送とみなし、
**枝番の小さいほう**だけを予約します (MX1 なら 23608)。中身が違うとき
(MX1 と MX2 で別番組) は題名が違うので、両方そのまま残ります。

番組表の画面が空の枝番を隠す仕掛け (`airing`) では足りません。あちらは
「番組が1つも無い局」を落とすだけで、**中身の入った写しは隠せない**ためです。

### 放送の延長に追従する

番組表の時刻は**予定**でしかない。野球が延びれば後ろの番組もずれるので、
時計だけで録ると尻切れになる。

追従の元は **EIT[p/f]** (いま流れている番組と次の番組)。番組表が使う
EIT[schedule] と違い、p/f は実際の放送に合わせて書き換わる。

**問い合わせる相手が要らない。** 録画しているチャンネルの TS にそのまま
流れてくるので、読むだけで分かる。追従のために別の口を開いたり、番組情報を
取り直したりしないので、**同時録画の本数にも響かない。**

いまの動き:

1. 録画は物理チャンネルを丸ごと開き、`ServiceFilter` でその局だけを書き出す
2. 同じ TS から EIT[p/f] を読む。`running_status` が「放送中」の番組が
   録画中のもの (event_id 一致) なら、その終了時刻を見る
3. **後ろへ動いていたら**予約と録画の終了時刻も動かす。動かさないとスケジューラが
   元の時刻で止めてしまう。**前へ動いても縮めない** (まだ流れているのに切ると
   取り返しがつかない)

EIT[p/f] を流さない局に当たっても、番組表の時刻どおりには録れる。追従できないだけ。

**残っている穴**: 延長したぶん後ろの予約と重なっても、録画中のものは競合計算の
対象外なので自動では調停されない。同じ物理チャンネルならエージェントが相乗り
させるので実害は無いが、別チャンネルでチューナーが埋まっていると後続が録れない。

## 消えないものは置かない

DBに残り続けるものには必ず期限を切る。1台のサーバで何年も動かすものなので、
放っておくと一覧が伸びるだけで探すのが遅くなる。

| もの | いつ消えるか |
| --- | --- |
| 番組表 (`programs`) | 終わってから1日 |
| 終わった予約 | 2週間 (取り消し・録り逃しか、もう録り始めたもの) |
| 削除済みの録画の行 | 同上 |
| エンコードの記録 | 同上。ただし**録画ごとに最新の1件は残す** (一覧の状態表示がそれを見ている) |
| 局 (`services`) | 消さない。代わりに画面から外す (上記) |
| ルール・設定・局ロゴ | 消さない (ユーザーが入れたもの) |

## この分け方で困るところ

- **チャンネルの顔ぶれだけは両方が知っている。** denpa の `services` (前回の取り込み
  時点) とエージェントの `channels` (いまのスキャン結果) で、スキャン直後は食い違う。
  これは隠さずチューナー画面に**両方並べて**出している。食い違い自体が
  「スキャンしたのに、まだ取り込んでいない」という情報になる
- **番組表を持っているので、集め直すまでは古い番組が残る。** 終わった番組は
  `pruneOldPrograms` が消すので、放っておいても数日で揃う
